\chapter{CN comparison and feedback}\label{chap:comparison-feedback}

\margintoc{}

In this chapter, I discuss the expectation versus reality of how usable a
verification tool for C \emph{can} be at this stage. I will start with my brief
and informal comparison between \kl{CN} and similar tools, based on my
experience of verifying \kl{pKVM}'s simpler early allocator, in \kl{CN},
\kl{VeriFast}~\cite{jacobs2011verifast} and
\kl{Frama-C}~\cite{pascal2012frama}. I will also discuss a \kl{RefinedC}
verification of the same, which was completed by the
developers~\cite{sammler2021refinedc}. I will not discuss
VST~\cite{appel2011verified}, due to lack of time and expertise for a fair
comparison. Part of this comparison was featured in~\textcite{pulte2023cn},
including the annotation overhead and execution times.

After that, I will compare \kl{CN} in more general terms to symbolic
execution tools which have some connection to C.

Lastly, I will discuss some feedback from industry partners. As an academic,
some of it seems unreasonable, but as an ex-industry professional, the
criticisms are much easier to concede. Given our goal of targeting kernel
programmers, we as academics want industry adoption for these tools, in which
case taking we need to take industry feedback seriously.%

\section{Early allocator}

\kl{pKVM} uses the \phantomintro{early allocator}
\href{https://github.com/rems-project/CN-pKVM-early-allocator-case-study}{{\emph{early}
allocator}} in \kl{pKVM} during initialisation, before switching over to the
aforementioned \kl{buddy allocator}. It is a simple allocator which just bumps
a pointer, with no support for reclaiming memory. It has a few functions for
initialising the allocator, clearing a page, allocating a cleared page,
getting the number of pages allocated, and so on. Here, I focus only on
the middle two.

\subsection{Early allocator in CN}

The proof for the early allocator was not part of CI for \kl{CN}, and so is
considerably out-of-date. Nevertheless, I will discuss a sample of the
code and specifications, because I expect updated specifications to look
similar.

The first function is for zeroing all the bytes in a page. This is implemented
in assembly in \kl{pKVM}, but for the comparison, I implemented a
version in C. The \kl{precondition} specifies that the function expects an array of
\cninline{Bytes} (not to be confused with memory bytes from~\cref{sec:mem-bytes-use}),
which is defined as a wrapper around
\cninline{RW<char>}. The \kl{postcondition} specifies the function returns an
array of bytes with value zero, expressed this way to avoid the use of the byte
array equality lemma mentioned in~\cref{fig:byte-array-eq-lemma}.

The loop invariant states that ownership moves from the former to the latter at
the loop index. This version of \kl{CN} required manually folding and unfolding
\kl(CN){predicates}, but inferred indices, and so the body of the loop features
annotations to do the former.

\cfile[fontsize=\footnotesize,breaklines,lastline=18,highlightlines={2-4,7-11,13,15}]{code/cn_early_alloc.c} % chktex 8

The second function allocates a zeroed page. It accesses two global variables,
\cinline{cur} which marks the current pointer of the allocator, and
\cinline{end} which marks the exclusive end of the allocator. It requires at
least a \cinline{PAGE_SIZE} difference between the two, and of ownership of the
bytes from \cinline{cur} to \cinline{end}, defined in an (omitted)
\cninline{EarlyAlloc} predicate. It ensures that it retains ownership of the
same \kl(CN){predicate}, but with new bounds \textemdash{} \cinline{cur} in the
\kl{postcondition} used to mean the its value at the \emph{end} of the
function, using \cninline|{cur}@start| to refer to the value at the start of
the function. And it ensures that the returned value is the base address of a
zeroed array of bytes. The body of the function simply unfolds and folds the
\cninline{EarlyAlloc} predicate, incrementing the pointer by the page size and
calling the \cinline{clear_page} function in between.

\subsection{Early allocator in VeriFast}

The verification of the early allocator in \intro{VeriFast}~\sidecite{jacobs2011verifast} is similar to the
\kl{CN} one. The main difference is that since \kl{VeriFast} does not support
\kl(CN){iterated separating conjunction}, it may require lemmas to manipulate the
inductive predicates involved instead. \kl{VeriFast} supports non-precise
assertions (\S\ref{subsec:precise-assertion}) as well, but does not support
ordinary disjunction for impure assertions for the same reason \kl{CN} does
not: to avoid backtracking in symbolic
execution.\sidenote{\url{https://verifast.github.io/verifast-docs/faq.html\#how-to-express-a-disjunction-p-or-q-in-an-assertion}}

In this example, the \cninline{characters_zeroed} predicate is recursively
defined, and is marked as precise. This allows \kl{VeriFast} to unfold
(\cninline{open}) and fold (\cninline{close}) the predicate automatically. The
loop invariant is expressed in Tuerk-style~\sidecite{tuerk2010local}, but
regular loop-invariants are supported too.

\cfile[fontsize=\footnotesize,breaklines,lastline=13,highlightlines={2,3,7,8}]{code/verifast_early_alloc.c}

If \kl{VeriFast} does not support \kl(CN){iterated separating conjunctions}, then how
does it support the indexing in this example without lemmas? The answer lies in
a surprising difference between how \kl{VeriFast} handles the semantically
equivalent subscripting \cinline{e1[e2]} and \cinline{*(e1 + e2)}.\sidenote{\url{https://github.com/verifast/verifast/issues/259}} % chktex 36

\begin{quote}
    \emph{Indeed, \kl{VeriFast} symbolically evaluates \cinline{*(start + i)} and % chktex 36
    \cinline{start[i]} differently. \cinline{*(start + i)} is symbolically % chktex 36
    evaluated just like any other dereference of a pointer to int, whereas
    evaluation of \cinline{start[i]} first looks for an
    \cninline{ints(start, ?n, ?vs)} chunk where \cninline{i <= n} and, if it % chktex 26 chktex 36
    finds one, returns \cninline{nth(i, vs)}. This is convenient for ``random % chktex 36
    access'' to ints-encoded arrays. If it does not find such a chunk, it falls
    back to looking for an \cninline{integer(start + i, _)} chunk, but the % chktex 36
    \cninline{start + i} computation is indeed not checked for overflow. This
    seems sound because if the integer chunk exists, it implies that the
    address is within the limits.}
\end{quote}

This example was a good lesson in how phrasing assertions
differently can lead to drastically different performance. Whilst the final
version uses a \cninline{characters_zeroed} predicate in the postcondition,
initially I used a more general \cninline{chars} predicate which lifts
characters in memory to a list. In that last argument, I wrote a call to
\cninline{create(count, item)}, a recursive function that I % chktex 36
defined, which creates a list of only \cninline{item} of length
\cninline{count}.

\kl{VeriFast} generally has good support for automation, and the ability to
state and prove lemmas (pure and resourceful) from within the system itself.
For pure lemmas, \cninline{lemma_auto}, marks it as available for use by
automation all the time, whereas \cinline{lemma_auto (expr)} automatically
applies the lemma when a precise predicate \cninline{expr} is in the context.

We need a lemma because deducing \cninline{unzeroed == nil == create(0,0)} % chktex 36
from the loop exit at \cninline{i == 4096}, via \cninline{length(unzeroed) == 0}, % chktex 36
is too difficult for the automation to manage unassisted. I marked the lemma
as automatic because I could not figure out where to place an annotation to
instantiate the lemma manually, nor figure out how to trigger it at the right
time. This worked, but it slowed down verification a lot: usable in
batch mode, a not usable interactively. There is no fallback to external
assistants.

To be clear: I know I am at fault, and am likely specifying things incorrectly.
I am quite confident such an example can be verified in \kl{VeriFast}. My point
is to draw attention to the (a) unexpected properties of nested structs and (b)
the difficulty of understanding any \kl{modes} or dataflow implicit in the
syntax. The issue with structs may be an intentional design choice to sidestep
handling exploding and imploding structs, which does require extra inference
and thus reduce performance.

Stepping back, \kl{VeriFast} uses an implicit, \adhoc{}, close-to-syntax,
semantics for C, which developers believe to be sound. This has the advantage
of allowing for some interesting, albeit confusing, heuristics such as
the array indexing example. However, it has the downside of missing a long tail
of features required for verifying real-world code, such as the following.
\begin{itemize}
    \item Struct literals/initialisers.
    \item Implicit type promotions (\eg{} \cinline{long long} to
        \cinline{unsigned long long}).
    \item Function types in struct fields.
    \item Taking the address of local variables.
    \item Expressive/accurate pointer provenance (it has basic support).
    \item \kl{UB} or \kl{unspecified} values for uninitialised reads.
\end{itemize}
Reflecting more broadly, what lessons can we apply to \kl{CN} from this brief
comparison? We see that \kl{separation logic}, \kl{moded} \kl(CN){recursive
predicates}, \kl(CN){lemmas}, \kl{pre-} and \kl{postconditions}, loop
invariants, \kl{proof annotations}, even the use of a subset of \kl(CN){C as a
proof language}, seem to come with the terrain of verifying C code. \kl{CN}'s
monadic syntax (\S\ref{sec:monadic-syntax}) sidesteps much of the confusion
related to \kl{modes}; the limited expressiveness of only allowing precise
predicates (\S\ref{subsec:precise-assertion}) has not affected substantial
verifications, and in fact enabled runtime testing of assertions with
\kl{Fulminate}~\sidecite{banerjee2025fulminate}. \kl{CN} will need to improve
its speed, visibility into the proof state and interactive replay to make
failed proofs less painful to debug.

\kl{CN}'s decision to support \kl(CN){iterated separating conjunctions} reduces the
need for lemmas and heuristics as \kl{VeriFast} uses, but does not eliminate
it, especially because inferring indices slows down verification. Automating
the \emph{common cases} of indexing, \kl(CN){predicate} unfolding, and
\kl(CN){lemma} applications, whilst retaining reasonable performance, and a
fallback to a fast but verbose manual mode, would allow \kl{CN} to adopt some
of the advantages of \kl{VeriFast}'s concision, without risking confusion in
novices.

\subsection{Early allocator in Frama-C and RefinedC}

Whereas \kl{VeriFast} is most similar to \kl{CN}, \kl{Frama-C} and
\kl{RefinedC} are one step removed. Both use undecidable logics, falling back
to Rocq for manual proof. For \kl{Frama-C}, the logic is a Hoare logic,
not \kl(logic){separation}, whereas in \kl{RefinedC}, the logic is an \kl{Iris} instance.

\intro{Frama-C}~\cite{pascal2012frama} has a smaller annotation overhead, though its lack of support for
\kl{separation logic} means the end guarantee is weaker than with the other tools.
It works by translating C programs into CIL~\sidecite{necula2002cil}. Its Hoare
logic verifier, WP, uses CIL as a front-end, and is parametric in the
memory model, allowing the user to trade away speed for
pointer manipulation expressiveness. It includes support for multiple
specifications per function, ghost parameters, arguments and code, and runtime
assertion checks, which amongst other things, can be used to error on
uninitialised reads. Frama-C was noticeably slower than \kl{CN} for the
early allocator (3.5s).

\intro{RefinedC}~\sidecite{sammler2021refinedc} is implemented inside Rocq atop \kl{Iris}, making its
\intro[TCB]{trusted computing base (TCB)} the smallest out of the tools mentioned
so far. However, its \kl{TCB} also includes its implicit, \adhoc{} semantics for C
based on the \emph{Caesium} kernel, over which its typing and automation
framework \emph{Lithium} operates. The rules are intended to be heuristic
rather than \kl{decidable}, with the main mode of operation inside a Rocq
session. Its annotation overhead is similar to \kl{CN}, but the performance is
much slower (16.7s).

\section{Other symbolic execution verifiers}

In this thesis, I have treated \kl{CN} as a \kl{refinement typing} system, but it is
equally valid to think of it as a compositional symbolic execution (CSE) tool.
CSE traces its origins back to Smallfoot~\sidecite{berdine2006smallfoot}, which
inspired many verification tools, but for the purposes of this section, I shall
focus only on tools that have some relation to \emph{verifying} C.

All the tools I discuss (bar VerCors) have some proof of soundness associated
with their approach, as well as some link to testing or inferring assertions.
The former is necessary for increasing expressiveness and reducing the
\kl{TCB}, and the latter is necessary for improving usability and usefulness
(by providing incremental benefit for incomplete specifications).

\subsection{Gillian-C}

\intro{Gillian}~\sidecite{santos2020gillian}, is a symbolic execution library
which supports both bounded whole-program execution (by inlining functions
calls to a certain depth) and compositional execution (of function
\kl{pre-} and \kl{postconditions}). It supports reasoning in both
over-approximate (OX) and under-approximate (UX) styles for proof and
bug-finding respectively~\sidecite{loow2024compositional}. The assertion
language is parametric: library-users provide `core predicates', and Gillian
provides predicate transformers, existential quantification and \kl{separating
conjunction}. Predicate transformers allow support for an \kl{Iris}-style
construction of state, with exclusive ownership, fractional permissions,
deallocation, partial maps and user-defined recursive predicates. For OX,
there are no restrictions on predicates, but for UX, to support specification
\emph{inference} using bi-abduction, the `core predicates' provided must be
\emph{strictly exact} (and the transformers used on them must preserve this).
The approach has been proven sound~\sidecite{loow2025compositional}.

% Caveat: folding (strictly exact) predicates in UX reasoning is unsound.

Note that, \kl{CN}'s syntax, in addition to enforcing mode correctness via
variable scoping, guides the instantiation of existential variables (which
guaranteed to be \kl{output arguments} of some \kl(CN){predicate}), and the order
of consuming resources from the context. Gillian instead opts for a more
traditional \kl{separation logic} syntax, and infers the order for consuming
resources automatically~\sidecite{loow2024matching}.

To use Gillian, one must translate programs from a source language (such as C,
Rust, or JavaScript) into the Gillian Intermediate Language (GIL). Its syntax
features mostly standard values, expressions and commands for
\emph{unstructured} control-flow. GIL's syntax is \emph{parametric} on a set of
actions for manipulating a symbolic state, both of which must be specified by
the user, with the help of several (optimised) building blocks provided by the
library. This approach has been used to support front-ends for C, Rust and
JavaScript. Henceforth, I shall only discuss the C front-end, Gillian-C.

Gillian-C uses CompCert~\sidecite{leroy2016compcert}, to compile C code down to
C\#minor, the latter's second IL (after Clight), and then translates C\#minor
into GIL.\@ It also adopts CompCert's memory object model as the foundation for
its symbolic state, but innovates on it with the introduction of \emph{symbolic
block trees}. Both the C model and the memory object model are \adhoc.
Symbolic block trees seem to both automate and speed-up much of the
memory-related reasoning, especially with respect to byte-level manipulations,
which require explicit annotations (\S\ref{sec:convert-bytes}) within \kl{CN}.

Gillian and its C front-end are well optimised, and I believe are likely an
order of magnitude faster than \kl{CN} on average. GIL would need to be
extended to support unsequenced and weakly-sequenced evaluation; the former is
conceptually straightforward but the latter is not. Gillian-C's
whole-program symbolic testing and UX specification synthesis found bugs in the
Collections-C library, an open-source library of generic data-structures for C
programs; its OX specification checking was used to verify encryption header
parsing in the AWS Encryption SDK for C, and found bugs along the way. However,
its emphasis on automation entails a surprising property: it is possible to
slow down verification by adding more annotations.

\subsection{Viper-based: VerCors and Gradual C0}

% https://dardinier.me/slides/tutorial_POPL25.pdf

\intro{Viper}~\sidecite{muller2016viper}, uses a similar IL-based approach for symbolic
execution, but uses a variant of \kl{separation logic}, implicit dynamic frames
(IDF)~\sidecite{smans2012implicit}, designed for \emph{object-based} languages.
The heap-model is fixed: it maps object-field pairs to values. Objects are
accessed via references which can be read and updated; it does not have
explicit de-allocation (conceptually, objects could remain allocated). Its
expressive logic supports user-defined recursive predicates, fractional
permissions, magic wands, and quantified permissions (which inspired the
initial scheme for iterated predicates in \kl{CN}). Like Gillian, the core
approach behind \kl{Viper} has been proven sound~\sidecite{dardinier2025formal}.

Arrays representing memory (and pointers with offsets into them) can be
encoded, but pointer arithmetic and byte-level reasoning is not directly
supported. IDF separates out \emph{accessibility} predicates \textemdash{} used
to specify the shape of the heap (permissions) \textemdash{} from
\emph{heap-dependent functions} \textemdash{} used to specify the contents of
the heap (values). Like \kl{CN}, this separates input arguments as parameters
and output arguments as the result (of the functions). However, most of the
time assertions must be self-framing (include all permissions to evaluate the
heap accesses in the assertion).

\kl{Viper} has the VerCors~\sidecite{blom2017vercors} front-end which supports
annotations on OpenCL/OpenMP/C code. \sidetextcite{blom2017vercors} say
`Support for basic features of the C and C++ languages works similar to the
verification of those features in Java'. Programs are annotated with
specifications and are then `encoded into the internal format of VerCors,
called COL, which is transformed in several steps into the input language of
\kl{Viper}'~\sidecite{oorschot2024first}. VerCors models pointer using a
block-offset scheme~\sidecite{haak2026verifying}.

\kl{Viper} is also forked by \intro{Gradual C0}~\sidecite{divincenzo2025gradual}.
C0 is a safe subset of C designed for education, and `gradual'
describes their approach to verification: soundly and efficiently
supporting incomplete specifications by proving as much as is possible statically,
and then inserting run-time checks for the remainder.
\sidetextcite{zimmerman2024sound} note that `IDF is particularly well-suited
for gradual specifications [because it] allows specification of heap values
while leaving more complex accessibility assertions unspecified'. They also
prove their core approach sound.

\subsection{Soteria-C}

Eschewing the IL approach, Soteria~\sidecite{ayoun2026soteria} is another
symbolic execution library. It has front-ends for
C (twice as fast as Gillian-C) and Rust, and, at the time of writing, an
experimental proof-of-concept one for \kl{CN}.
Soteria-CN\sidenote{\url{https://github.com/soteria-tools/soteria-cn}} uses
the same modified \kl{Core} as \kl{CN}, and can be up to 50x faster than \kl{CN} on small tests cases for
singly- and doubly-linked lists. The speed-up seems to \emph{increase} with the
size of the program, though \kl(CN){iterated predicates}, inductive datatypes and
pure \kl(CN){functions} are unsupported, so larger and more representative
examples may not be so impressive.

Soteria-C uses \kl{Cerberus}' Ail rather than \kl{Core}, because Ail retains more
of the original program structure and thus makes it easier to apply
heuristics as optimisations.\sidenote{Though of course, it keeps implicit much
subtlety, for example, integer promotions and evaluation order.} For example,
\kl{Cerberus} will elaborate the \cinline{&&} operator (in Ail) to an if-expression
(in \kl{Core}) to capture the fact that it is short-circuiting and may have
side-effects. To handle this possibility soundly, Soteria-C will fork the
symbolic execution path, even though this would be unnecessary for most code.
Another example is local variables: \kl{Cerberus} models variables as heap-allocated
in case their address is taken. As is, this precludes the possibility of
modelling locals (more efficiently) outside the heap \emph{until} their address
is taken. Both of these are fixable with more annotations on the \kl{Core}
program during elaboration (or an analysis afterwards), but show that without
care, the explicitness of \kl{Core} can be a downside.

\section{Industry feedback}\label{sec:industry-feedback}

My stated thesis is that building a verification tool for C which can handle
\kl{low-level} systems programming is within reach: two parts engineering and one
part theory (\S\ref{sec:thesis-stmt}). The aspirational goal of \kl{CN} is to
bring the cost of C verification down from ``a Rocq programmer who knows
separation logic to a systems programmer who is proficient with functional
programming''~(\S\ref{sec:cn-intro}). This simultaneously ambitious from a
research stand-point, but timid from an industry stand-point, even for systems
programmers who are willing to walk-the-talk with regards to correctness.

This is borne out by feedback from BAE Systems and Galois, industry partners
on a DARPA project to verify `a fictitious airborne
unmanned platform that represents a notional high-consequence national security
system' using \kl{CN} (amongst other
tools).\sidenote{\url{https://github.com/GaloisInc/VERSE-OpenSUT}} Galois in
particular raised several points of feedback on seeing \kl{CN} in its current
state, which sharpen the need to keep a holistic view of usability in mind for
tools like this.

For example, they said they were \emph{``skeptical that a developer that wrote
bad code would be capable of writing specs that get the code right''}. For
researchers in verification, the standard response is that a specification is
intended to be higher-level and easier to understand, but this takes for
granted how familiar we become in thinking in abstract mathematical ways
amenable to proof, which may not apply to the target audience. In some sense,
the real thing pointed to by this comment is that writing correct code
(including specifications) is hard, and we have made a tool that makes the
difficulty very obvious and painful, whereas before it could be more easily
ignored.

This is something that even the Rust community faced with beginners feeling
like they were ``fighting the borrow checker'', but more experienced users
eventually learned to appreciate the extra rigidity after seeing its benefits.
If tools like \kl{CN} are to succeed, they must address these pedagogical and
cultural issues as well as the technical ones.

Not only might the experience of using \kl{CN} be a show-stoppingly unpleasant
reality check, it might also be asking too much: though the \kl{monadic syntax}
(\S\ref{sec:monadic-syntax}) is theoretically elegant, there was
concern \emph{``that the learning curve is too steep, \eg{} akin to learning a
new programming language or worse''}. Guilty as charged. Though lightweight
specifications for \emph{testing} in C are feasible, it is unclear if the
same is true for \emph{proof}.

% Specification languages are mathematical to enable reasoning in proofs;
% programming languages are operational to run on computers, and human
% languages are implicit for ease of communication. The expectation that one
% could be used for another is simultaneously natural for novices and
% technically unfeasible. Whilst we can, should and are currently exploring
% different syntax approaches, especially in consultation with our industry
% users, the basic issue will remain. Overcoming this will likely come down to
% a mix of framing and experimenting rather than any deep technical choices.

Another challenge is communicating when it is appropriate to consider using
\kl{CN}.\@ Our partners have \emph{``a lot of programs with large legacy code bases,
\eg{} millions of lines of C.  No one is going to go back to annotate that
much code''}. When they ask \emph{``How does that fit with \kl{CN}?''}, its
important that the answer be qualified in terms of when is verification a good
fit, rather than ``all code should be verified''.

A large, reasonably reliable system for day-to-day use is not a good candidate
for verification, but a small, mission-critical piece of code where the cost of
errors and the difficulty of preventing them are both high, is much more likely
to be. For the foreseeable future, \kl{CN}'s comparative advantage will be providing
much greater assurance for code where existing methods do not suffice, rather
than trying to out-compete where they do.

Even in economically appropriate use cases, \kl{CN}'s proof mode is an
all-or-nothing endeavour and gives one very little to work with. Feedback along
this line, and currently out of scope for this project, is the \emph{``need for
a supporting tool for making suggestions for  specifications''}, though we have
observed that \kl{Fulminate}'s ability to execute \kl{CN} specifications, has,
with property-based testing, provided a gentler gradient for integrating
specifications into a developer workflow~\sidecite{aamer2026code}.

There are indications that \kl{CN} is on the right track, and has advantages
worth highlighting when pitching and evolving CN.\@
Industry developers care about \emph{``specific security concerns''} such as
\emph{``input validation, memory safety on embedded systems, and maths-heavy
algorithms''}. Even for non-embedded systems, \kl{CN} would do well to develop
tools and user interfaces which demonstrate the step-change advantage of
exhaustive verification, above test-based memory safety tools such as Valgrind.

Another desiderata our partners mentioned, aside from correctness, is
performance (of the code being verified). Here the case is less obvious, but
possible: making it easier to write correct concurrent code, may make it more
likely that programmer will do so to speed up an application, in the same way
that the absence of a whole class of resource management bugs makes it more
likely that people reach for Rust when trying to do the same.

Based on this feedback, \kl{CN} has potential to be used widely, but needs to
do the following:
\begin{itemize}
    \item Learn from the Rust approach to teaching and error messages.
    \item Experiment with specification syntax, to make it more approachable.
    \item Explore imperative specification languages for proof.
    \item Set clear expectations around the cost and benefit and appropriate
        use-cases for verification.
    \item Allow incomplete specifications and look into suggesting them too.
    \item Support input validation and maths-heavy algorithms, and other core
        use cases industry say they care about.
    \item Demonstrate a clear advantage over existing testing-based memory
        safety tools, with concrete examples.
    \item Assist with concurrency to confer performance benefits.
\end{itemize}

\section{Summary}

Here, I summarise the many (incompatible, or at the very least, impractical)
directions \kl{CN} could pursue based on the comparison with other tools
and the industry feedback. I leave evaluating and synthesising these points
to the next chapter.
\begin{itemize}
    \item Improve performance by 10x.
    \item Trace type checking steps for replay.
    \item Improve syntax concision and approachability.
    \item Improve error messages.
    \item Infer/suggest specifications.
    \item Reduce the \kl{TCB}.
    \item Support using \kl{CN} `out-of-the-box'.
    \item Focus on industry-favoured use cases, such as mathematics,
        input-validation, memory safety beyond current tools, and concurrency.
\end{itemize}

\chapter{Lessons learned}\label{chap:expectations}

\margintoc{}

In this chapter, I synthesise some lessons from the previous chapter's
comparison of \kl{CN} to similar tools, and industry feedback. I lay out
achievable standards of usability for \kl{CN} \emph{going forward}, with an
emphasis on how \emph{new projects} can avoid several pitfalls. Only where I
explicitly say so are the suggestions intended to be retrospective.

\section{Work backwards from examples}

Prior to~\textcite{pulte2023cn}, \kl{CN}'s guiding test during its development
was the \kl{pKVM} \kl{buddy allocator}. Its pervasive aliasing and
computed pointer accesses made verifying the allocator a novel and
substantial research contribution. However, it \emph{also} limited \kl{CN}'s
design: features were only considered and implemented insofar as they got
\kl{CN} closer to verifying the allocator.

Whilst this approach produced a successful paper, it also over-fitted \kl{CN}.
We accrued significant technical (see below)
and design debt (see~\cref{chap:inform-impl}), which hindered specifying and
verifying simpler and more conventional examples, such as those now in the
CN tutorial~\cite{pulte2024tutorial}.

% Many of the features mentioned in~\cref{chap:inform-impl} might have been
% anticipated earlier, for example, unifying the syntax for
% functions, predicates and specifications. These features were built separately
% over time and as a result have ended up similar but incompatible. For example,
% one of the many incompatibilities is the separate scopes for predicates and

% desugaring.\sidenote{\href{https://github.com/rems-project/cerberus/issues/288}{Cerberus\#288}}

With only slight irony, my point is that \emph{test-driven development is
exceptionally useful when implementing a verification tool}. This bore out in
my experience in implementing \kl{CN-VIP}: writing examples, and informally (but
rigorously) working through how they ought to be specified, helped enormously
in guiding my intuitions and highlighting problems early on.%
\margincite{pulte2023cn}\margincite{pulte2024tutorial} I conjecture a
broader range of smaller examples escalating to the \kl{buddy allocator} would
have been similarly helpful.

\section{Design with a formalism}

Whilst there are some changes which would have been difficult to
pre-empt initially, for example, the change in
inference
scheme,\sidenote{\href{https://github.com/rems-project/cerberus/commit/7c2c0a364a4373e4eb109f32d01cc9584f51e81f}{Cerberus
7c2c0a36.} This was motivated by reducing the annotation burden for folding
and unfolding predicates, which turned out to be heavier than the annotations
saved by inferring indices.} or the switch to the \kl{monadic syntax}
(\S\ref{sec:monadic-syntax}), there are a few design decisions which might
have benefited from more scrutiny prior to implementation.

\subsection{Calling conventions affect syntax}

% Kayvan: There is no text in the standard explicitly saying whether to
% allocate at call site or in the body. there is ISO C11 §6.5.2.2#4 that says:
%
%   An argument may be an expression of any complete object type. In preparing
%   for the call to a function, the arguments are evaluated, and each parameter
%   is assigned the value of the corresponding argument.
%
% I suspect the wording "in preparing" is why I elaborated everything in the

By default, \kl{Cerberus} elaborates C function calls by allocating
and initialising temporary storage for parameters \emph{at the call site},
and then \emph{passing their
pointers} to the callee. This led to verbose
and awkward specifications, where functions had to (a) \kl{own} their
parameters, and (b) ensure they were unmodified, so that the objects at the
call-site remained unaffected.

This was tedious and error-prone, so we changed the
elaboration\sidenote{\href{https://github.com/rems-project/cerberus/commit/772173d6432c86b029fd1bb993b8dc83b80c96c0}{Cerberus
772173d6}} and \kl{CN}\sidenote{\href{https://github.com/rems-project/cerberus/commit/186e4e42a75cad2222d441ce608fc1dc84cc7b98}{Cerberus
186e4e42}} correspondingly, resulting in duplicated effort. Had we spent some
time looking at small sample \kl{Core} programs, and testing out a formalism on
it, we might have anticipated the issue sooner.

\subsection{Error reporting}

Most of the time, \emph{any} programming language tool will be fed an incorrect
or incomplete program. The standard approach to dealing with this is to layer
a tool's stages such that only well-formed programs pass from one stage to
the next. Within the context of \kl{CN}, the main stages are:
\begin{itemize}
    \item parsing,
    \item desugaring,
    \item elaboration of C into \kl{Core},
    % \item Translation of \kl{Core} to $\mu$\kl{Core}
    \item base type/well-formed specification checks, and
    \item \kl{per-function} constraint and resource inference and checking.
\end{itemize}

Such a strategy is understandable, and makes the system robust because each
phase assumes the invariants ensured by the previous, and establishes new ones.
It also makes the implementer's job easier, but
code is written once, read a lot, and used orders of magnitude more.

The problem is that users (rightfully) expect to be able to get feedback on
their program at multiple stages of development, and getting one error at a
time slows down the edit-check cycle. Of course, multiple errors can also
overwhelm the user, but it is easier to limit them once they are already
supported, than it is to support them if they do not exist.

In the ideal case, users should be able to execute a whole pipeline of stages
even in the presence of errors from the first; it would be very impressive if
\kl{CN} could do resource inference in the presence of parse errors
\emph{within the function it was checking}, or even just in other parts of the
program.

This is unrealistic for \kl{CN}, because it would require substantial
re-engineering of \kl{Cerberus}. A realistic goal
is to raise the lower bar of recovery, by designing each step such that
\emph{it avoids stopping at the first error}. For example, up until relatively
recently, \kl{CN} stopped at the first error in the first failing function,
\emph{even though it was designed to support \kl{per-function} checking}.

It should be possible to improve \kl{CN}'s incremental
error-handling, without resorting to a full rewrite of the implementation
starting from the parser. Below, I conjecture a process which could be
applied in an incremental way to existing projects, so the benefit is
proportional to the effort invested.
\begin{itemize}
    \item Pick the most important stage.
    \item For every (or each important) sort, a \emph{hole}
        construct~\sidecite{omar2017hazelnut}.
    \item Update the rest of the stage to handle this hole.
    \item If the subsequent stage supports holes, consider joining them up.
\end{itemize}
If, like in \kl{CN} proof mode, the last (semantic analysis) stage is the most
interesting and expensive one, this suggests working backwards through each
stage.

To be clear, I am not talking about \emph{incrementalising} \kl{CN}, though
support for holes could make this easier. And I am not saying that \kl{CN}
should have been formalised or implemented with an elegant system for
the maximum amount of error recovery and collection.

What I am saying is that for every \kl{CN} annotation, there is an opportunity
to support multiple errors through multiple stages, dependency analysis, and
feature gating, and that there are concrete benefits to writing code to with
this in mind from the start.

Consider the failed bit-vector update for the \kl{buddy allocator}
(\S\ref{sec:buddy-failed-bv}). One of its major pain points was (tediously)
switching \emph{every integer in every datatype, \kl(CN){function},
\kl(CN){predicate}, \kl(CN){pre-}, and \kl(CN){postcondition}} to a bit-vector; without
this, despite being designed for \emph{\kl{per-function}} checking, \kl{CN}
would stop at the first integer/bit-vector mismatch. On just this update, a few
extra weeks of implementation effort early on would have saved \emph{months} of
scarce time:
\begin{itemize}
    \item manually calculating the dependency structure, starting at the
        leaves, and commenting out everything else,
    \item manually testing for regressions, and
    \item noticing the slow-down in verification.
\end{itemize}

I conjecture inspiration from the below two papers will prove fruitful
to investigating and guiding the theory and implementation of multiple
errors for \kl{CN} in the future.
\begin{itemize}
    \item \citetitle{zhao2024total}~\sidecite{zhao2024total}.
        This paper defines a \kl{bidirectional} gradual
        type system for types and expressions (including holes), and a total
        procedure to mark expressions with \emph{all possible} type errors. It
        then adds constraint solving on top of the type holes, so that
        inconsistent type constraints are localised \emph{exclusively to holes
        and marked types and expressions}, by tracking the program origins of
        unknown types. The relevance of this paper is its principled approach
        to all of the above.
    \item \citetitle{spies2024quiver}~\sidecite{spies2024quiver}.
        This paper also uses a two way flow of
        information familiar from \kl{bidirectional} type checking, but describes it
        using \kl{separation logic} terminology: generalising bi-abductive reasoning
        to \emph{abductive deductive verification}. It symbolically evaluates a
        program using a context of \kl{separation logic} assertions, proving
        everything it can and assuming everything it cannot. The specifications
        (`predicate transformers') it infers are analogous to \kl{CN}'s
        \kl(CN){function types}. The relevance of this paper is its similar
        domain to \kl{CN}.
\end{itemize}
Though designing calculi in this way may seem like it increases the amount
of work involved for reporting errors, in actuality, it simply makes
implementation choices around error reporting \emph{explicit in the formalism}.

\subsection{Elaborate with care}

Elaboration and program transformations such as \kl{A-normalisation} can
affect the accuracy of source locations. On top of this, if handled without
care, generated variables can also end up not associated to any source location
the user wrote, and can be difficult to interpret in a counter-example. \kl{CN}
used to \kl{A-normalise}, but does not any
more,\sidenote{\href{https://github.com/rems-project/cerberus/commit/21808139bda2ee320756c71eb22dbd57d0986f97}{Commit
21808139}.} because it was difficult to relate such variables to \kl{Core}
expressions. The situation has improved a bit with more helpful auto-generated
names and no \kl{A-normalising}, but the solution is \adhoc{}, and the gap between
\kl{Core} and C still remains.

Whilst I have some ideas on how to improve the situation,\sidenote{Low-hanging
    fruit is to associate bound variables to the location of the sub-expression
    they are binding
    (\href{https://github.com/rems-project/cerberus/issues/270}{Cerberus
\#270}).} a systematic treatment of source location information through
elaboration would be helpful to understand what it would mean to have, and what is
required for, maximal source location accuracy. A suitable theory would provide
guidance on the different kinds of source locations, (points, ranges, cursors,
preprocessed, elaborated, fresh/dummy) and how they should be preserved in
different manipulations, such as alpha-renaming and substitution and (partial)
evaluation. An important feature would be accurately tracking the origins of
new source locations \emph{from within the implementing code}, because it is
quite confusing and difficult to debug a bad source location. Ideally, it would
also explore how one might track which terms have valid locations in a rich type
system like OCaml's or Haskell's.

\section{Software engineering}

\kl{CN} has been developed for around 6 years at the time of writing. It has
had multiple contributors, some of whom have left the project now. Like any
project, it benefits from good software engineering practices; here, I focus on
the important ones.

\subsection{Test for any visible regressions}

For a long time, \kl{CN} did not have any regression testing and so features
which were implemented, but accidentally broke later, went unnoticed.
Another substantial benefit to regression testing is that it enables and assists
with fairly large-scale refactors. Regression testing is also very helpful when
multiple people are working on overlapping parts of the project, so that
changes which accidentally break other things are picked up \emph{before} being
merged in to the main branch.

Regression testing should not only capture the ability of the program to
execute with or without errors, but also \emph{the output} in \emph{both} of
those cases. If a test is intended to fail before a \kl{CN-VIP}-related change,
and it continues to fail after the change, it is often good to check that it is
failing \emph{for the same reason} (\eg{}, we would not a division-by-zero test
changing its behaviour after a change to the \kl{memory object model}).

To assist with this, I wrote a small but increasingly sophisticated Python
script\sidenote{\href{https://github.com/rems-project/cerberus/pull/703}{Cerberus\#703}.}
to run a given program, in a particular configuration (consisting of a name, a
filter on file names, and arguments to the program) and capture and check the
return codes and all the output, against a pre-existing file. If there is a
difference, the program will raise an error, and also provide a diff the
developer can apply \emph{across the affected files} if the change is expected.

\subsection{Profile early and often, at the right level}\label{subsec:profile}

% Aside from this, even in the absence of \kl{VIP} related performance issues,
% \kl{CN} is still about an order of magnitude slower than we would like it to
% be, though the causes of this are not clear, the plan of being able to rely
% on performant SMT solvers with decidable queries has not paid off quite as
% well as we would have liked.

A slow heavily-automated verification tool is effectively unusable, and a lack
of good measurement makes it difficult to understand why \kl{CN} is slow and
how to fix it.

Prior measurements were \adhoc{}, and revealed that most of the time is spent
in the solver, which we believe to still be the case. However, we need better
granularity on the subject, to answer the following.
\begin{itemize}
    \item What is the distribution of times per call to the solver?
    \item What part of \kl{CN} generates the slowest problems?
\end{itemize}

We have some performance benchmarking now, enough to demonstrate that enabling
\kl{CN-VIP} is slow and soundly reducing bounds checks\sidenote{By replacing them
with liveness checks.} reduces execution time (\S\ref{sec:vip-perf}). However, we
do not have good insight into why this is the case. The measurements
are noisy and coarse \textemdash{} the script only measures the total execution
time for running each regression test once.

As I mentioned before, performance remains the main reason that it is nigh-on
impossible to update the \kl{pKVM} \kl{buddy allocator} verification after \kl{CN}'s
bit-vector update (\S\ref{sec:buddy-failed-bv}). \kl{CN} is still an order of
magnitude slower than we would like or expect it to be, and so fixing this, and
setting up infrastructure to prevent backsliding, is a key priority.

\subsection{Error with pride, do not crash}\label{sec:error-msgs}

I will begin this sub-section with a quote from Sean Chen, co-shepherd
of the Rust Error Handling Working Group~\sidecite{chen2020anatomy}.

\begin{quote}
\em
This, to me, really speaks about culture; rustc and the developers [\ldots]
are all eager to help you, to provide helpful context,
to provide hopeful errors, to make your job, your workflow, as a developer,
easier. If you have to spend less deciphering error messages, that is more time
that you can be productive on the code you are writing.

[\ldots] I think technology takes a little bit of a back seat, [\ldots] all of
these code examples [\ldots] ingenious in a sense but at the end
of the day I don't think it is [\ldots] more ingenious than anything else
inside of rustc [\ldots] It really is a question of culture, more specifically,
I think the culture of the community is what informs the technology.
\end{quote}

Rust compiler (`rustc') developers have a clear definition and explanation of
the structure of an error
message.\sidenote{\url{https://rustc-dev-guide.rust-lang.org/diagnostics.html}}
On top of that, as demonstrated by the quote, they have a culture of
willingness to be helpful.

Whilst \kl{CN} is different from Rust in many ways, they do share the
commonalities of being \kl{low-level} systems programming language with complex
rules dictating whether code is accepted or rejected, and as such, there is
much to learn from their example.

Of course, there are large differences in the amount of resources available for
both, with \kl{CN} being an academic project with limited industry support,
whereas Rust is a mainstream project. And so, I will adjust my recommendations
accordingly.

\paragraph{Use rich datatypes for errors.} \kl{CN} inherits many of Cerberus'
error message datatypes and explanations, which quote the standard. Whilst
quoting thus is impressive, most users will not understand the \kl{standard's}
jargon (\cref{fig:lsp-extra}), and so it needs to be hidden by default, and
eventually translated into more accessible language. The fact that these are
represented by a datatype makes it easy to add this functionality later. It is
easier to add more information and not use it than it is to plumb it
through later.

\paragraph{Avoid showing crashes and backtraces.} \kl{CN} does an admirable job
on controlling the effects exposed by various parts of the code by wrapping
most effectful operations in a typing monad. However, there are a few cases
which result in crashes which are predictable and avoidable.
The most important reason for avoiding this is that \emph{the
output from \kl{CN} can and will be used by other tooling, to provide editor
services and GUIs}.\sidenote{For example,
\href{https://github.com/rems-project/cerberus/issues/286}{cn \-\-json
can produce non-JSON output (Cerberus\#286)} and
\href{https://github.com/rems-project/cerberus/issues/221}{Flycheck
support (Cerberus\#221)}.}\label{sn:gui-issues} At the time of writing, there are 185 uses of
\ocamlinline{failwith} and 297 uses \ocamlinline{assert} in the code
base, all of which can print backtraces, and make it difficult for
tools to build on top of \kl{CN}. Whilst it is possible to work
around this, by calling into \kl{CN} as an OCaml library instead,
this increases the overhead of developing tooling for \kl{CN}.
These come from two sources.
\begin{itemize}
    \item \textbf{Unimplemented features.} These are extremely common when
        building any large project, and so this should by no means be
        considered an exceptional condition. Instead, an error message should
        make it clear what feature is not implemented, and \emph{where in the
        source code} it rose from.
    \item \textbf{Assertion or invariant failures.} Again, whilst these signal
        bugs, bugs are common, and they need to be handled gracefully. Whilst
        backtraces may be helpful, they should not be visible by default.
\end{itemize}

\subsection{Log, do not debug}

Another regretful aspect of \kl{CN}'s development is its over-reliance on debug
output as a substitute for a user-interface and well-defined structured logs.
There are about 255 instances of debug related code in \kl{CN} today.

To be clear, I am not saying that it is necessary to invest heavily in
producing beautiful and intuitive GUIs from the start \textemdash{} that
depends on the resources available and priorities of the project.

What I am saying is that clear visibility is a trait of good software, and
unstructured debug output, whilst occasionally helpful, is rarely the correct
tool for this job. Instead, it makes much more sense to record
the sequence of actions and their effects at each step, in a reasonably
structured format so that (a) its output format can be wholly separated from the
recording and (b) processing the output can be wholly separated from both.

Structured logging is \emph{especially} useful in the presence of mutating
state, monadic OCaml code (which removes all useful information from any
backtraces), and inverted control flow with explicit continuations. Whilst
there is some \adhoc{} logging for recording \kl{memory actions}, used for the
HTML output, a disciplined logging scheme would facilitate the following.
\begin{itemize}
    \item Profiling the solver (\S\ref{subsec:profile}).
    \item Validating resource inference (\S\ref{sec:better-foundations}).
    \item Experimenting with the user-interface.
\end{itemize}

The last one in particular has been the subject of multiple issues related to
GUIs (see note~\ref{sn:gui-issues}). It was also one of the blockers for
further progress on an LSP\sidenote{Editor-agnostic language-server protocol.}
server\sidenote{\url{https://github.com/rems-project/cn-lsp-server}} and
client\sidenote{\url{https://github.com/rems-project/cn-lsp-client}} I
prototyped (\cref{fig:lsp-state,fig:lsp-extra}).

\subsection{Miscellaneous}

There are a myriad of other small but useful practices which have or would have
been useful regarding \kl{CN}'s development.
\begin{itemize}
    \item Gate substantial changes underneath a flag. Whilst this
        does risk making the code more complex, and accruing unused flags and
        options, the cost of breaking updates is too high, which I discussed in
        depth in \fancyref{subsec:handling-large-changes}.
    \item Use version control \emph{well}. Thankfully, using version control
        these days is convenient and common, though there is an art to
        using it well.
        \begin{itemize}
            \item Break up large features into small commits. This makes them
                easier to test, review and merge piecemeal.
            \item Rebase at least daily. This simplifies the commit history and
                avoids error-prone and time-consuming merges later on.
            \item Write informative commit messages. Commit messages are just
                as much documentation as any other part of the code. A good
                message summarises the change and \emph{explains why}
                certain decision were made.
            \item If working on an online platform, work on forks, rather than
                branches. This prevents clutter on the primary repository.
        \end{itemize}
    \item Automate and enforce a continuous-integration (CI) pipeline. The
        regression testing and profiling should be there to \emph{decrease}
        developer load, rather than increase  it.
    \item Automate and enforce code formatting. Whilst no code-formatter will
        please everyone, the easiest to read (and diff) code is consistent
        code. This saves a remarkable amount of time and effort.\sidenote{Git
            has a feature to ignore certain commits when using its blame
            features, which has minimised the impact on formatting all of the
        \kl{CN} code.}
\end{itemize}

\section{Get source locations right}

% As result of this failed attempt, I came to appreciate all the above. I ended
% up spending about one month plumbing through source location information
% throughout the core datatype in \kl{CN}, as well as fixing the lexer and
% parser to be more robust and have extensible error messages.

Source location information is the cornerstone of a useful error
message, without which an error is close to useless. Unfortunately, early
versions of \kl{CN} did not give this crucial data its due, leading to an
incredibly poor user experience. This is all the more disappointing because
within the OCaml ecosystem, the \intro{Menhir} parser generator makes getting this
sort of thing right a lot easier than one might initially
expect~\sidecite{pottier2016reachability}.

\subsection{Keep the lexer and parser simple}

Initially, support for \kl{CN}
annotations in comments was implemented by relying on global
mutable state.\sidenote{A feature of ocamllex that seems to be
under-appreciated is that each rule is an OCaml function and can be passed
arbitrary parameters, thus avoid the need to use global mutable state.}
This prevented code re-use, complicated the code and introduced subtle
location bugs because of accidentally re-using shared mutable token
buffers. I simplified the lexer and parser to avoid this, and in the
process improved and unified the error-reporting for parsing C and
\kl{CN}.\sidenote{\href{https://github.com/rems-project/cerberus/pull/252}{Cerberus\#252}.}

\subsection{Investigate strange source locations}

Strange source locations are
bugs which deserve to be investigated, or at the very least, have their
triggers documented. One such
issue\sidenote{\href{https://github.com/rems-project/cerberus/issues/382}{Cerberus\#382}.}
uncovered a subtle interaction between the `lexer hack' used to parse
C11~\sidecite{jourdan2017simple}, and a token buffer feature offered by
\kl{Menhir} for more helpful error messages. Again, the issue was mutable state,
accidentally shared across what should have been separate, fresh instances
of the lexer. I solved this by staging the creation of the lexer and its
state, and making that explicit in its
API.\sidenote{\href{https://github.com/rems-project/cerberus/commit/c970a43b7126560b229fb55c32ce22bfbc5d23f2}{Cerberus
c970a43b}.}

\subsection{Use source locations once you have them}

Once source locations are accurately recorded by the front-end, then it is
important to use them in later stages. Initially, \kl{CN}'s core term type,
used for representing SMT terms, did not support source location information.
This made for a very poor and frustrating user experience in common cases, such
as ill-formed terms, or failing constraints in a \kl(CN){specification} or a
\kl(CN){predicate}.

Because the type representing this term was large, and used in many places,
this made adding the location information after the fact much more tedious and
painful, and adding new code only exacerbates this further. Eventually, I spent
about one month fixing this
problem.\sidenote{\href{https://github.com/rems-project/cerberus/pull/225}{Cerberus\#225}.}
Whilst in some cases, threading source location through was obvious,
in many cases it is not. The question then arises: is it better to have all
terms have source location information, even if some of it is approximate,
or to have missing location information, but be confident about the ones
which are not missing?

Though the user-experience of the latter seems superficially worse than the
former, \emph{a bad source location is worse than no source location}, for both
the user, and the developer who has to debug it later. Hence, missing source
location information is preferable, \textbf{so long as it documents where in
the implementation code} the missing location comes from. Here is an example,
were a \kl{resource request} has failed. Below is an error message which says that

some \kl(CN user-defined){predicate} is not being unfolded enough, or that a

point to where this local was declared, where it disappeared, and the

information, it is safer to (a) not attempt to display any location at all or,
(b) provide a dummy one, which points to its origin in the implementation.

\subsection{Write parser error messages if feasible}

Initially, a parse error in \kl{CN} would simply signal `unexpected token' and
exit with no other information, except a ballpark source location which was
sometimes right. This was less than helpful for a number of reasons, most
notably not telling the user what token \emph{was} expected. It is possible to
\emph{generate} inelegant, but informative parse error messages based on
the error message format output by
\kl{Menhir}.\sidenote{\url{https://gallium.inria.fr/~fpottier/menhir/manual.html\#sec\%3Amessages\%3Aformat}}

I shall now explain how I did
this.\sidenote{\href{https://github.com/rems-project/cerberus/commit/127758764cd6efdabaaaddb60eabf40575864117}{Cerberus
12775876}.} The first line shows the sentence used to get to the error state.
This is useful for \kl{Menhir}, but is not considered to be a good source of
information for writing an error message. This is because the information in
the comments shows the production which is being parsed, and at which point in
it the error occurs. More than half of error states (629) have exactly one
production, and in this case, I generate an error message as shown at the
bottom of the excerpt.

\begin{minted}[fontsize=\footnotesize,linenos,numbersep=6pt,breaklines]{py}
cn_statements: ASSERT WHILE
##
## Ends in an error in state: 1585.
##
## cn_statement -> ASSERT . LPAREN assert_expr RPAREN SEMICOLON [ .. ]
##
## The known suffix of the stack is as follows:
## ASSERT
##

parsing "cn_statement": seen "ASSERT", expecting "LPAREN assert_expr RPAREN SEMICOLON"
\end{minted}

Of course, it is better to fill these and the remainder (593) manually, as I
demonstrated for one
case.\sidenote{\href{https://github.com/rems-project/cerberus/issues/245}{Cerberus\#245}.}
Details of how best to do so are in the \kl{Menhir} manual, along with
examples and links to how CompCert uses it for its C parser (proof that
the approach can be scaled). For the cases I did not auto-generate, I
output a message which says that an error message is missing for the state
(identified by a number), and that it can be added in the stated file. In any
case, I set up \kl{Menhir} to show exactly where and between which tokens
parsing failed, which is often enough for experienced users to fix errors.
\kl{Menhir} also provides functionality to check and merge its auto-generated
error messages with existing ones, so that the latter can be preserved despite
changes to the grammar.

\subsection{Consider a custom pre-processor}

The bane of any academic C tooling seems to be the preprocessor. Whilst it
faithfully preserves line numbers, and this tends to be good enough, it does
not preserve column information, which in most cases, leads to inaccurate error
messages on any code which is inside, or after a macro expansion.\sidenote{The
macro call and expansion may have the same length if one is lucky.}

We are caught between two unappealing choices: either present the error message
in terms of the preprocessed code, thus retaining accuracy but sacrificing
relevancy, or present the error message (with the wrong location) in terms of
the original code, retaining relevancy but not accuracy. \kl{CN} currently does
the latter, and given the fact that macros do often represent constants, or
function-like abstractions~(\S\ref{subsec:takeaway-features}), we would also
like to have them supported in \kl(CN){specifications} as well.

There are no easy solutions to this,\sidenote{Even CompCert just calls a
user-specified preprocessor.} but it appears to be a solvable problem. For
example, there maybe ways to coax GCC or Clang to output debug tokens whilst
preprocessing a file, which could be input to a custom lexer which takes the
tokens \emph{and the source location information} and connects it to the
\kl{Cerberus} front-end. Or, one could write a Clang plugin, or use the Boost
pre-processing library Wave to attempt a similar trick, with more control over
the resulting format. In both cases, it looks like it should be possible to
preserve comments too, but this will not allow running the preprocessor
\emph{inside} \kl{CN annotations}.

It may however, be feasible to implement a custom C preprocessor, using a
relatively straightforward pseudo-code algorithm by Dave Prosser, \emph{which
formed the basis of the prose specification of macro expansion in the C89/ANSI
C standard}~\sidecite{prosser1986complete}. This algorithm is annotated and
explained~\sidecite{spinellis2008complete}
by~\sidetextcite{spinellis2010cscout}, the author of the CScout refactoring
browser for C, who was struggling to implement a C preprocessor correctly for
about five years, before finding a reference to an algorithm by Dave Prosser.
Spinellis could not find the algorithm, so he emailed Prosser who
obliged.\sidenote{\url{https://www.spinellis.gr/blog/20060626/}}

Not only is there an algorithm, Spinellis' implementation is available
online\sidenote{\url{https://github.com/dspinellis/cscout/blob/master/src/macro.cpp}}
along with a suite of test
cases\sidenote{\url{https://github.com/dspinellis/cscout/tree/master/src/test/cpp}}
and expected
outputs.\sidenote{\url{https://github.com/dspinellis/cscout/tree/master/src/test/out}}
There is even expertise within the programming language research community on
the algorithm, since it was recently discussed as being closely related to the
strategy for checking termination for expanding type definitions in type
expressions in OCaml~\sidecite{chataing2024unboxed}. Based on this, I used
Claude Code to implement a working proof-of-concept within three
days.~\sidenote{\url{https://github.com/dc-mak/cerberus/tree/internal-cpp-plan}}
The biggest challenge was not correct macro expansion (including inside magic
comments), but for supporting good, Clang-like error messages (when an
error occurs inside a chain of expansions), due to a limitation of \kl{Menhir}.

\section{Process counter-examples smartly}\label{sec:counter-ex}

Whilst \kl{counter-examples} have the potential to be very useful for explaining
abstract proof errors, currently they do not live up to that in \kl{CN}.
I wrote the criteria below based on real usability issues we have encountered
with counter-examples, but it is not clear to me how achievable they are. The
\href{https://github.com/Z3Prover/z3/issues/3964}{`unsat-core'} feature of Z3,
or the
\href{https://cvc5.github.io/blog/2024/04/15/interfaces-for-understanding-cvc5.html}{`model
core'} feature of CVC5, may be relevant. In the idea world, we would aim
for `dynamic witnesses for static errors', as described
in~\sidetextcite{seidel2016dynamic}.
\begin{itemize}
    \item \textbf{Multiple \kl{counter-examples} may need to be shown.}
        If there is more than one \kl(CN){predicate} in the context with a
        matching name, but unequal arguments, then the counter-example will be of
        the most recent failure. A user is unable to understand why a
        \kl(CN){resource} did not match one of the ones in the middle based on
        the presented values.
    \item \textbf{Unconstrained/irrelevant variables should be excluded from the
        \kl{counter-example}.} A given error will have many variables
        irrelevant to the whole program state, but the \kl{counter-example}
        will uniformly give assignments to all of them. This makes the user
        work harder to filter out irrelevant details.
    \item \textbf{\kl{Counter-examples} should be consistent.} The
        \kl{counter-examples} are not consistent with respect to the
        irrelevant variables, and this can be confusing to the user too.
    \item \textbf{\kl{Counter-example} variables should be easy to relate to
        program variables.} Currently, \kl{counter-example} variables are
        presented in terms of symbolic variables \emph{from the
        \kl{precondition}} of the function rather the values of the program
        variables at the point of failure. This means the user has to trace and
        work out values at that point for themselves.
    \item \textbf{\kl{Counter-example} variables should be easy to relate to
        \emph{prior source steps}.} In general, the \kl{counter-examples}
        represents the failure at the \emph{latest} step, and what users would
        like would be to see how a \kl{counter-example} would evolve \emph{at
        every step leading to that}.
    \item \textbf{\kl{Counter-example} values should be small.} Large numbers
        in \kl{counter-examples} are difficult to comprehend. Ideally
        they would be replaced with smaller, easier to read and track numbers.
\end{itemize}
