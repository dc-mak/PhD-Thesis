In~\cref{sec:c-lang}, I discussed how the \kl{ISO standard} of C attempts to
reconcile the competing forces of portability, hardware control, and
optimisation. I also mentioned that it is ambiguous, and diverges from \kl{de
facto} C. Its rules are challenging to follow manually, and complex to
express over C-like languages; existing tools thus variously simplify control
flow, variable scoping, loose evaluation order and pointer manipulation.

\kl{CN}'s headline goal (\S\ref{sec:cn-intro}) is to work with pre-existing C
programs, ones whose correctness will rely on said rules. Yet,
expressing those rules over a C-like language would quickly make it unwieldy,
and thus hamper its other goal of reducing the expertise required for
verification.

So, \kl{CN} builds upon the \kl{Cerberus} executable and empirically validated
semantics for C~\sidecite{memarian2022cerberus}. It thus benefits from both the
\emph{accuracy} and the \emph{usability} of this semantics for both \kl{ISO}
and \kl{de facto} C. \kl{Cerberus} \kl(Cerberus){elaborates} C's complexity to
\emph{\kl{Core}}, a first-order functional language with a few special
constructs.

Additionally, \kl{CN} is intended to be used like a \emph{type system} in an
IDE than a program logic in a proof assistant. Ideally, instead of seeing
intermediate goals in a sophisticated separation logic, and being proficient
with a range of inference rules and automation tactics, a user sees their C
program, scattered with predictable and lightweight annotations, in an editor
which either indicates success, or a helpful error message.

% Aside from the fact that the notion and mode of use of a type system is more
% familiar to most programmers, this approach also allows \kl{CN} to use and
% advance the extant literature on building refinement type systems on top of
% existing languages.
%
% This type system approach also leads to other desiderata and their
% corresponding responses.

A good type system aims to minimise obvious annotations and be predictable on
the necessary ones; to do so, \kl{CN} tracks the flow of information
systematically, using a \kl{bidirectional} approach. A type system will also
need automation to not burden the programmer with proving obvious things.
Similar to \kl{VeriFast}~\sidecite{jacobs2011verifast},
\kl{Gillian}-C~\sidecite{santos2020gillian}, and
\kl{Frama-C}~\sidecite{pascal2012frama}, \kl{CN} enlists SMT solvers to help. A
type system must also terminate, even with SMT solver, so \kl{CN} restricts the
expressiveness of the assertion language and SMT queries. Lastly, to track and
manage resources in C, the type system needs to be substructural.

\kl{CN}'s assertion language aims to be expressive for verifying real-world
programs, but restrictive to ensure termination (and speed), and intuitive for
systems programmers who are familiar with functional programming.

In this part, I formalise and prove type-safe \kl{Kernel CN}: a
\kl{bidirectional} type system for \intro{ResCore}, a \kl{let-normal} version
of \kl{Core}. It is a formalism for \kl{CN} which assumes all quantifiers are
explicitly instantiated, and all \kl{resource manipulations} have \kl{proof
terms} with \kl{linear} types. It does not require proof terms for logical
entailments (which, by construction, are \kl{decidable}).

I also formalise two related \kl(CN){elaboration} algorithms: one for quantifier
instantiations, one for \kl(kernel){iterated} predicate indices. I do so to explain the
\emph{principles} of \kl{resource inference}, since the implementation
frequently changes; I have not embarked on any proofs for either scheme.

In~\fancyref{chap:formal-background}, I expand upon \kl{CN}'s constraints and
design decisions, explain the relevant features of \kl{Core}, and cover the
necessary background to understand \kl{CN}'s syntax and \kl{Kernel CN}.

In~\fancyref{chap:kernel-grammar}, I explain \kl{Kernel CN}'s types, and
their relation to \kl{CN}'s syntax. I also explain \kl{ResCore} and
its relation to \kl{Core}, by example.

In~\fancyref{chap:kernel-statics}, I explain the \kl{Kernel CN} typing rules
for \kl{ResCore}. It lacks inference and so is simpler to prove sound. Since it
handles the majority of C, the entire system is very large; I only discuss
the main features. I also show the aforementioned \kl(CN){elaboration} algorithms, which
infer the information assumed by \kl{Kernel CN}.

In~\fancyref{chap:kernel-soundness}, I discuss the key definitions, lemmas and
proof sketches used in a syntactic proof of type safety for \kl{Kernel CN}. Of
note are the definition of substitution, the novel structure of the heap, and
the interaction between resource terms and the heap.

In~\fancyref{chap:inform-impl}, I discuss how the formalisation brings clarity
to many implementation questions around lifting restrictions or adding new
features.

In~\fancyref{chap:kernel-alternative}, I conclude this part by sketching an
alternative presentation of the \kl{CN} type system, \kl{MiniCN}, which is
closer to both C as a surface language and the \kl{CN} implementation. I
demarcate the challenges of \emph{not} using \kl{ResCore} from the challenges
which seem to be inherent to designing a type system for a C-like language.

\chapter{Background: Cerberus and CN design}%
\label{chap:formal-background}

\margintoc{}

In this chapter, I set out \kl{CN}'s design goals and origins, recapitulate the

\section{CN design goals and constraints}%
\label{sec:cn-goals}

Aiming for \emph{``a verification tool whose aspirational goal is to lower the
prerequisites of C verification from a Rocq programmer who knows separation logic to a
systems programmer who is proficient with functional programming''}
(\S\ref{sec:cn-intro}) helps narrow down the large design space of such
tools.

There were two reasons for picking this goal. First, it was an unexplored area
in the design space. Second, we wanted to verify the \kl{pKVM} hypervisor, developed
by Google~\cite{deacon2020virtualization} (and its precursor, Hafnium).

To explain \kl{pKVM}, I need to explain its context: the Android operating
system. Android runs on billions of devices worldwide and so handles an
enormous amount of sensitive data. Security updates are paramount, but each
device runs its own kernel: up to half the code is \emph{not} Android's version
of the Linux kernel. This makes testing and deploying updates, challenging,
expensive and slow: it takes more than 18 months for new releases of Linux and
to roll-out to devices. Aside from security, fragmentation and fewer
upstreamed features and fixes, are also concerns.

% \url{https://youtu.be/7novnkldMmQ}

Some of these concerns have been mitigated with the introduction of
Generic Kernel Images
(GKI),\sidenote{\url{https://source.android.com/docs/core/architecture/kernel/generic-kernel-image}}
which provide a small and stable kernel ABI \emph{for a particular long-term
release} of Android. Even so, both
the kernel (20 million lines of code), and device drivers shipped by vendors,
are too large to be a reasonable trusted computing base.

Some vendors try to use hypervisors to isolate the kernel from the rest of the
system \textemdash{} such as `secure' hardware storing sensitive data
\textemdash{} by running Android and other hardware components in separate
virtual machines. They also use hypervisors for non-security reasons, such as
partitioning memory at boot-time, direct memory access, or arbitrary code
execution (at a more privileged level) outside of Android. Using hypervisors
just \emph{shifts} the attack
surface,\sidenote{\url{https://googleprojectzero.blogspot.com/2020/02/mitigations-are-attack-surface-too.html}}
and also increases fragmentation.

Similar to GKI, the proposed solution is to standardise the hypervisor.
There is already a mature hypervisor inside the Linux kernel: the Kernel-based
Virtual Machine (KVM)\@. It lets a host kernel dynamically allocate virtual
machines for guests, and protects the host from them. However, initially, it
did not protect guests from the \emph{host}. This is a problem because the
guest could be running code for a secure hardware component (\eg{} a biometric
authenticator), but the host could be a compromised version of Android, so an
attacker could still get access to sensitive information.

To solve this, Google, as part of the Android Virtualisation
Framework,\sidenote{\url{https://source.android.com/docs/core/virtualization/whyavf}}
is developing a \intro[pKVM]{protected KVM
(pKVM)},\sidenote{\url{https://lpc.events/event/7/contributions/780/}} which
runs \emph{underneath} the kernel,\sidenote{\kl{pKVM} utilises the Armv8 exception
    levels (EL) feature, which defines four levels of increasing privilege. EL0
    is used for Android applications, EL1 is used for the kernel, EL2 is used
for the hypervisor, and, EL3 is not used.} and ships \emph{as part} of the
kernel image. This allows \kl{pKVM} to remain very small, only supporting a few
functions (such as virtual memory management), and rely on the Linux kernel to
manage the rest, such as scheduling, device drivers and power management.

If successful, this would make the attack surface much smaller in code, but
much larger in number of devices. It is in this context that my research group
and Google saw the opportunity to verify a small hypervisor, \emph{on an
ongoing basis}. A one-and-done verification which takes an army of PhD students
and postdocs a few years to verify is not worth the investment; a tool which C
kernel programmers can understand, use and maintain security-critical proofs
with, would be.

This background explains \kl{CN}'s headline goal, and also
clarifies some of the \emph{constraints} on its design:
\begin{itemize}
    \item Because kernel programmers wrote the code, and use
        conventional compilers to build and run it, we cannot hope
        some \adhoc{} model of C is sound \textemdash{} we want and need
        something captures C's real-world behaviour as
        closely as possible.
    \item Because it will be used by kernel programmers, we want a story that
        is acceptable to them. They are very smart and capable people, who do
        not have the time or support to get up to speed with separation logic
        and interactive proof assistants. Nor are they amenable to changing
        their development or company's product delivery workflows
        substantially. I conjecture that a ``fancier type system'', which runs
        as part of their continuous integration (CI) pipeline, has a better
        chance of being adopted.
    \item Similarly, because the annotations will be read by kernel
        programmers, and upstreamed to Linux, we want them to be minimal and
        easy to understand. Achieving this requires careful management
        about the flow of information in the type system, and automating
        as many obvious things as feasible.
\end{itemize}

In turn, these constraints feed into concrete technical choices which \kl{CN}
makes:
\begin{itemize}
    \item To capture real-word C behaviour, \kl{CN} uses the \kl{Cerberus}
        empirically validated semantics.
    \item To integrate into existing workflows, \kl{CN} appears to users
        as a fancy type system.
    \item To retrofit the type system on top of the existing one, and in
	particular to ensure erasure, \kl{CN}'s type system uses
	\kl{refinement types}.
    \item To automate proofs of constraints, \kl{CN} relies on SMT solvers.
    \item To ensure \kl{decidability} (termination), and aim for reasonable in
        practice performance, \kl{CN} follows a \emph{\kl{liquid typing}}
	discipline, restricting the queries it sends to the SMT solver.
    \item To minimise constraint annotations, \kl{CN}'s type system is
        formalised and implemented in a \kl{bidirectional} style.
    \item To check the resource management of C programs, \kl{CN}'s type
        system uses \kl{linear} types, using the grammar of separation
        logic assertions.
    \item To stay within the \kl{liquid typing} discipline \emph{and} avoid
        quantifier instantiation annotations, \kl{CN} uses precise assertions
        with a \kl{mode}d discipline for predicate arguments.
    \item To make such precise assertions with a mode discipline easier to
        read, write and explain, \kl{CN} uses a \emph{monadic}
        syntax.
\end{itemize}

\section{Cerberus and Core for a usable and accurate C semantics}%
\label{sec:cerberus-core}

\intro{Cerberus} is an empirically validated and executable semantics for
\kl{ISO} and \kl{de facto} C, specifically C11. A detailed comparison
between it and other C semantics is available in the Related Work chapter
of \sidetextcite{memarian2022cerberus}, but for the purposes of \kl{CN},
it suffices to say it captures real-world C.

\kl{Cerberus} is vital for \kl{CN} because it expresses this executable
semantics in a \emph{relatively simple first-order functional language},
\kl{Core}. Its modus operandi of \kl{compositional} \kl(Cerberus){elaboration},
makes explicit many tricky parts of C.

\kl{Cerberus} handles
the strange scoping and control flow (of jumping \emph{into} a loop) of
\cref{fig:perplexing-ub}. The program parses and passes static checks;
its illegality is revealed during execution because of
subtle, dynamically checked rules (see caption). Whilst contrived, any long C
function which has exception handling and retry behaviour, could make the same error.
\kl{Cerberus} also supports C's mutable and potentially aliasing
variables, and its myriad other \kl{undefined} or unspecified behaviours,
\eg{} loose evaluation order and coercions respectively.

\section{Core grammar}\label{sec:core-grammar}

\kl{Cerberus} elaborates C to \intro{Core}, a not-too-large calculus where
each construct is designed to capture some peculiarity of C. It is split into
two fragments, a \kl(Core){pure fragment} (\cref{fig:pure-core-grammar}) and an
\kl(Core){effectful one} (\cref{fig:effectful-core-grammar}); the former is
embedded into the latter.

The \kl(Core){pure fragment} forbids memory operations, but
does include the effect of undefined behaviour explicitly with the
\coreinline{undef} operator. It handles
things like implicit type conversions or bounded arithmetic. As visible from the
grammar, the pure part is very much a first-order functional language with
recursive functions, with some C-specific constructs such as pointer
arithmetic on arrays/members and \kl{specified/unspecified}/integer values.

The \kl(Core){effectful fragment} supports memory operations, sequencing constraints,
and exotic control flow with a goto-like operator used for elaborating
C's iteration and \cinline{goto} statements. The distinction between the \kl(Core){pure}
and \kl(Core){effectful fragments} is unrelated to the distinction between expressions and
statements in C:\ both are \kl(Cerberus){elaborated} to \kl(Core){effectful expressions} (for example,
\coreinline{PtrEq} which tests for pointer equality).

I discuss \coreinline{memop} in more detail in
\fancyref{chap:mem-model-explained}. For now it suffices to say that the
operations are effects, part of the memory interface \kl{Core} uses to abstract
over different memory object models.

Next are the constructs related to sequencing. A more precise treatment
of this is given later in \fancyref{sec:weak-seq}. As per
\sidetextcite{memarian2022cerberus}, \emph{Each use of an action is either
``positive'' (the default case) or ``negative'' (if the action appears in the
syntax as the operand of the \sm{\cnkw{neg}} operator)}.
\begin{itemize}
    \item \sm{\cnkw{neg}(\cnnt{action})} marks side
        effects (see text to note~\ref{sn:side-effect}).
    \item \sm{\cnkw{unseq}(E_1, \ldots, E_n)} is unsequenced evaluation of each
        sub-expression.
    \item \sm{\cnkw{let}\ \cnkw{strong}\ \cnnt{pat}\ \cnkw{=}\ \cnnt{E}_1
        \ \cnkw{in}\ \cnnt{E}_2} sequences all memory actions performed by
        \sm{\cnnt{E}_1} before those performed by \sm{\cnnt{E}_2}.
    \item \sm{\cnkw{let}\ \cnkw{weak}\ \cnnt{pat}\ \cnkw{=}\ \cnnt{E}_1
        \ \cnkw{in}\ \cnnt{E}_2} only only sequences positive memory actions of
        \sm{\cnnt{E}_1} before those performed by \sm{\cnnt{E}_2}. In other words,
        any negative memory actions (\sm{\cnkw{neg}(\cnnt{action})}) performed by
        \sm{\cnnt{E}_1} are unsequenced with respect to all memory actions
        performed by \sm{\cnnt{E}_2}. A race only occurs if unsequenced memory
        actions have overlapping footprints (\S\ref{sec:weak-seq}), and is
        deemed \kl{UB}.
    \item \sm{\cnkw{bound}(\cnnt{E})} evaluates its argument \sm{\cnnt{E}} and
        then clears its footprint (\S\ref{sec:weak-seq}). It marks the
        boundary of a C expression as a statement.
\end{itemize}

The \coreinline{par} construct is for spawning threads. The
\coreinline{nd} construct models non-determinism as required or
implied by aspects of the standard.

The \coreinline{ccall} and \coreinline{pcall} constructs are for
calling \kl(Cerberus){elaborated} C functions and \kl{Core} procedures (effectful functions)
respectively. They differ only in how the name of the procedure to be called is
found, with \coreinline{ccall} using the memory interface to do so.

The (thread-local) Core operational semantics is defined in
\textcite{memarian2022cerberus}; I present the key rules below.
It is a small-step transition from a configuration to either undefined
behaviour or a new configuration: \sm{\langle h, E, \kappa
\rangle \rightarrow (\textsc{Undef} \mid \langle h', E', \kappa' \rangle)},
for a heap \sm{h}, effectful expression \sm{E}, and call stack \sm{\kappa} (list of
evaluation contexts \sm{C}). These steps rely on evaluating pure expressions (in a
big-step style) to either undefined behaviour or a value \sm{\cnnt{pce} \Downarrow
(\textsc{Undef} \mid \cnnt{value})}.

For example, \coreinline{pcall} pushes the enclosing evaluation context \sm{C}
on to the call stack \sm{\kappa}, evaluates its arguments to values, looks up the
function body \sm{E}, substitutes the parameters for the values, and then executes
the body.

{\small%
\[
\inferrule[{[PCall]}]
 { \mathrm{funmap} ( \cnnt{name} ) = \left(\cncomp{x_i {:} \beta_i}{i}\right).\ E \\
   \cncomp{\cnnt{pce}_i \Downarrow \cnnt{value}_i}{i} }
 { \left< h , C\left[ \cnkw{pcall} \, \left( \cnnt{name}, \cncomp{\cnnt{pce}_i}{i} \right) \right] , \kappa \right>
   \rightarrow \left< h , \left[ \cncomp{\cnnt{value}_i / x_i}{i} \right] E , C \Colon \kappa \right> }
\]}

Conversely, \coreinline{return} pops an evaluation context off of the call stack,
applies it to the returned value, and proceeds with the resulting expression.

{\small%
\[
\inferrule[{[Return]}]
  { }
  { \langle \cnnt{h} , \cnkw{pure}(\cnnt{value}) , C \Colon \kappa \rangle
    \rightarrow \langle h, C [\cnkw{pure}(\cnnt{value})] , \kappa \rangle }
\]}

The \coreinline{save} operator is \kl{Core}'s way of introducing named
continuations with default arguments. This is the aforementioned \cinline{goto}-like
operator, which is used to elaborate C's iteration and
\cinline{goto} statements.
\begin{itemize}
    \item \sm{\cnnt{id}} is the name, also referred to as the label.
    \item \sm{x_1, \ldots, x_n} are parameters which in scope in \sm{E}.
    \itemAP{} \sm{e_1, \ldots, e_n} are \intro{default arguments} for those parameters.
\end{itemize}

\textbf{The label of a \coreinline{save} expression is scoped to its
enclosing \kl{Core} procedure.} This means there are three ways of reaching
one.

\begin{itemize}
    \item Forward jump, with a \coreinline{run} operator.
    \item Backwards jump, with a \coreinline{run} operator.
    \item No jump, via evaluation of the enclosing expression.
\end{itemize}

A \coreinline{save} expression evaluates by instantiating
and substituting its parameters in its body. The instantiation
depends on how the expression was reached. If it was via the
\coreinline{run} operator, then the instantiation is
with the arguments of the same. If it was via the enclosing expression,
then the instantiation is with the \kl{default arguments}.

Formally, \coreinline{save} (reached normally, via its enclosing
expression) evaluates its default arguments to values, and then substitutes
those into its body.\sidenote{Since this does not
manipulate the heap or the call stack, it is phrased purely as expression
reduction, with a separate, omitted rule to lift expression reductions to
thread-local reductions.}

{\small%
\[
\inferrule[{[Save]}]
  { \cncomp{\cnnt{pce}_i \Downarrow \cnnt{value}_i}{i} }
  { \cnkw{save} \, \cnnt{id} \left( \cncomp{x_i \cnkw{:=} \cnnt{pce}_i}{i} \right) \, \cnkw{in} \, \cnnt{E}
    \rightsquigarrow \left[ \cncomp{ \cnnt{value}_i / x_i }{i} \right] E }
\]}

Reaching the same \coreinline{save} via a \coreinline{run} 
is more complicated. Like a \coreinline{pcall}, it evaluates its arguments
to values and looks up the label \sm{\cnnt{id}}. The \sm{\mathrm{labelmap}} is
precomputed on a per-procedure basis by \kl{Cerberus} during \kl(Cerberus){elaboration}.
Unlike \coreinline{pcall}, the result of the lookup is \emph{a context}
\sm{C_{\cnnt{id}}} and an expression \sm{E_{\cnnt{id}}}. It substitutes the values
for the parameters in \sm{E_\cnnt{id}}, \emph{discards the current context} \sm{C},
and uses \sm{C_\cnnt{id}} instead. All the while, the call stack \sm{\kappa} is unchanged.

{\small%
\[
\inferrule[{[Run]}]
  { \mathrm{labelmap} ( \cnnt{id} ) = \left(\cncomp{x_i}{i}\right).\ C_{\cnnt{id}} [ E_{\cnnt{id}} ] \\
    \cncomp{\cnnt{pce}_i \Downarrow \cnnt{value}_i}{i} }
  { \langle h , C\left[ \cnkw{run}\, \cnnt{id} \left( \cncomp{\cnnt{pce}_i}{i} \right) \right] , \kappa \rangle
    \rightarrow \left< h , C_{\cnnt{id}} \left[ \left[ \cncomp{\cnnt{value}_i / x_i}{i} \right] E_{\cnnt{id}} \right] , \kappa \right> }
\]}

In the context of \kl{CN}'s \emph{partial} (termination
insensitive) reasoning, control \emph{may} return from a
\coreinline{pcall}/\coreinline{ccall}, but will \emph{never} return
from a \coreinline{run}.

\subsection{Discussion}\label{subsec:elab-discussion}

A few things are noteworthy about \kl{Cerberus}' C to \kl{Core} \kl(Cerberus){elaboration}:
\begin{itemize}
    \item The \kl(Cerberus){elaboration} is \intro{compositional}: each function, block,
        statement and expression is \kl(Cerberus){elaborated} in isolation, based only
        on its parts, and follows the structure of the original C program.
    \item Each variable (function argument, local, and global) is uniformly
        handled as living on the heap and gets its own storage via the
        \coreinline{create} function. Reads, writes, and de-allocations are
        represented with \coreinline{load}, \coreinline{store},
        \coreinline{kill} respectively.
    \item Loose evaluation order (for example between the operands of a \cinline{==})
        is represented using \coreinline{unseq} and \coreinline{let weak} constructs.
    \item \kl{UB} is made explicit in the syntax of the program.
\end{itemize}

\kl{Compositionality} is just as important, as the \kl{Core} being a
first-order functional language. This makes it straightforward transport
annotations on C source, to annotations on \kl{Core}.

If \kl{Cerberus} \kl(Cerberus){elaborated} C to a dataflow graph,
such transporting might be difficult. \kl{Pre-} and \kl{postconditions} should
be easy, but it is unclear how one would handle loop invariants, \coreinline{goto} annotations, and
\kl{CN statements}.

In principle, the \kl{compositional} mapping also ensures that errors in
verifying \kl{Core} can be related back to useful locations in the original C.
In practice, this requires a good amount of engineering to accomplish
(\S\ref{sec:error-msgs}).

Another challenge is distance between C and \kl{Core}. Reporting SMT assertion
failures in terms of what the user wrote is difficult when it mentions
variables introduced by the \kl(Cerberus){elaboration}, or when the assertion itself is
introduced by \kl{CN} (\S\ref{sec:counter-ex}).

This concludes the background related to \kl{Cerberus}; I now discuss the
background related to the \kl{CN} type system.

\section{Decidable refinements for retrofitting and counter-examples}\label{sec:decidable-refinements}

\kl{Core} already has a \kl{bidirectional} type system which
\kl{Cerberus} uses as a sanity check for the \kl(Cerberus){elaboration}. It has not been
used for a proof of soundness \textemdash{} this would just be a sanity check on the
dynamic semantics.

\begin{marginfigure}
    \small%
    \centering
    \begin{mathpar}
        \inferrule{ }{\Gamma \vdash \cnkw{undef} (\cnnt{UB\_name})\Leftarrow \cnnt{T}}
    \end{mathpar}
    \caption{Checking rule for the \coreinline{undef} pure expression as
    mentioned in \textcite[p91]{memarian2022cerberus}.}\label{fig:core-ub-typing}
\end{marginfigure}

For example, \coreinline{undef} checks against any type
(\cref{fig:core-ub-typing}).\margincite{memarian2022cerberus}
This is because \kl{UB} terminates the dynamic
semantics; it does not return control. Remember, a valid C program is one which
has no \kl{UB}, but such a type system cannot guarantee its absence.

To do that, we need to enrich the context to track the (control flow) path
conditions. Then, the typing rule for \coreinline{undef} would
require that the context be inconsistent (able to prove false), meaning
the expression is unreachable: consider a trivial example
of nested \mintinline{py}{if} statements in~\cref{fig:dead-code}.

\begin{figure}[h]
    \inputminted[linenos,numbersep=6pt,mathescape,fontsize=\small]{py}{code/dead_code.py}
    \caption{A contrived example on how tracking control flow assumptions
        within a program could be used to prove the impossibility of
        undesirable behaviour.}\label{fig:dead-code}
\end{figure}

From the outer \mintinline{py}{if}, we know that \mintinline{py}{x >= 5}, so
the check \mintinline{py}{x < 4} will always evaluate to \mintinline{py}{False}.
Thus control will always flow to line 12 (and return) instead of line 9 (and
raise the exception). Tracking path conditions during
type checking means that the context is inconsistent at line 9.

To track such constraints in a typing context, we need to talk about program
variables and values \emph{at the type level}. This requires richer types which
can depend on program terms. However, we \emph{do not} want the converse; we
should be able to recover the original program and dynamic semantics by erasing
the types after type checking. Enriching the type of an existing language
whilst retaining erasure is known as \intro{refinement
types}~\sidecite{jhala2021refinement}.

Such types should not force the user to write obvious proofs,
such as \sm{x \geq 5 \wedge x < 4 \Rightarrow \bot}. Unfortunately,
first-order logic with arithmetic is undecidable: type checking may not
terminate on certain programs. Given that there are real-world programming
languages\sidenote{\href{https://hacklang.org/}{Hack},
\href{https://forums.swift.org/t/swift-type-checking-is-undecidable/39024/34}{Swift},
and F\sm{^*}~\cite{swamy2016dependent}.}\margincite{swamy2016dependent} which have
undecidable type systems, but work fine in practice, is this a problem?

Whilst `\kl{decidable}' does include exponential or NP-complete time complexity, we
conjecture that such SMT theories are faster, and more \emph{stable}: the
performance is consistent across irrelevant or small changes to a proof. We
also conjecture that problems generated by type checking will be limited by
human cognitive capacity and thus be reasonably small, especially compared to the
typical uses of SMT solvers. Thus \kl{CN} aims for \kl{decidability} as an imperfect
proxy.

\kl{CN} ensures \kl{decidability} by restricting its use of quantifiers as per the
\intro{liquid types}~\sidecite{rondon2008liquid} approach. In practice, this means (a)
all quantifiers must track program values (function arguments for \sm{\forall},
return values for \sm{\exists}) and (b) constraints sent to the SMT solver are
free of quantifiers. When this too restrictive, \kl{CN} offers a lemma
mechanism (\S\ref{sec:lemma-prover}) to export and prove facts in the
Rocq~\sidecite{CDT2024} proof assistant.

Aiming for \kl{decidability} also lets \kl{CN} extract concrete
\kl{counter-examples} to explain constraint failures in terms of concrete
values for \kl{Core} program variables (a subset of which correspond to C
program variables).

\section{Bidirectionality for taming subtyping}\label{sec:bidir-subtyping}

With \kl{liquid types}, we can use an SMT solver to automate tedious proofs.
However, implications induce a \kl{subtyping} relation in such a type system, which
means we have a \emph{subsumption rule}, as shown in~\cref{fig:subsumption}. As
presented, the rule is \emph{not} syntax-directed, and so raises the question:
when should it be used?

\begin{marginfigure}
  \small%
  \begin{mathpar}
      \inferrule{\Gamma \vdash e \mathrel{{:}} \{\, x \mid \phi (x) \,\}  \\ \phi (x) \Rightarrow \phi' (x) }
                {\Gamma \vdash e \mathrel{{:}} \{\, x \mid \phi' (x) \,\}}
  \end{mathpar}
  \caption{Subsumption rule using for a system with subset types and logical
      implication \sm{\Rightarrow} as the \intro{subtyping} relation.}\label{fig:subsumption}
\end{marginfigure}

Revisiting~\cref{fig:dead-code}, imagine a type system where contexts
\sm{\Gamma} are either \sm{\cdot} or \sm{\Gamma, \{\, x \mid \phi (x) \,\}}, and
\sm{\phi} represents some constraint on \sm{x}. In particular, we are not
accumulating path conditions in the context, just the variables and their
subset types. We would like to prove that function \mintinline{py}{gt_zero}
satisfies its postcondition, \sm{\{\, \mathsf{ret} \mid \mathsf{ret} > 0 \,\}}
without raising an exception.

Working forwards, we start with a type \sm{\{\, \mathsf{x} \mid \top
\,\}}. Inside the function, we are checking both branches because we cannot
statically rule one out. In the true case, we \emph{refine} the type to
\sm{\{\, \mathsf{x} \mid \mathsf{x} \geq 5 \,\}}. The subsumption rule is not
syntax-directed, so we are free to apply it now. Doing so, we have have \sm{\{\,
\mathsf{x} \mid \mathsf{x} > 0 \,\}}, because \sm{\mathsf{x} \geq 5 \Rightarrow
\mathsf{x} > 0}. Unfortunately this means we cannot rule out the
\cinline{else}-branch and the exception within.

Whilst quite contrived, it illustrates the importance of knowing when and how
to use the subsumption rule. We could ask users to annotate the code at each C
statement, but this would be extremely burdensome: we would have traded the
tedium of proving simple facts for the tedium of writing obvious annotations.

\kl{CN} chooses a middle-ground: it requires annotations on functions and
loops, as a minimum. Socially, we believe this is easy to explain and accept,
since programmers already write documentation for the former. And technically,
function and loop annotations enable \emph{compositional verification}.
Verifying a large code base can be parallelised and fast, because it can
sidestep the need to do complex and potentially slow loop-unrolling or
inter-procedural analyses.

Concretely, this means we would like \emph{check} types at function calls,
function returns, loop entry, and loop exit, from the top down, and
\emph{synthesise} types everywhere else, from the bottom up. This is exactly
what \kl{bidirectional} type systems were designed to do (Sections 4.4 and 4.6
in~\sidetextcite{dunfield2021bidir}). Moreover, it gives a clear principle of
when to apply the subsumption rule (call the SMT solver): at the boundary
between synthesis and checking (\cref{fig:simple-bidir}).

\section{Linearity to manage (non-leaky) resources}\label{sec:linearity-manage-resources}

\kl{Decidable refinements} and \kl{bidirectional} typing are sufficient to
prove the absence of \kl{UB} in \kl{Core}'s \kl(Core){pure fragment}
(\S\ref{sec:core-grammar}), but we need more to do the same in its \kl(Core){effectful
fragment}, to handle memory-related \kl{UB}.

In \fancyref{sec:sep-logic-intro}, I showed how \kl{separation logic} can be used to
reason about the behaviour of heap-manipulating imperative programs. We can
embed its propositions into a type system too, but we have to be careful.
Typically, type systems are \intro{intuitionistic}; this means we can
duplicate, forget, and re-order assumptions freely. In formal logic, these are
enabled by \emph{substructural} rules, known as \intro{contraction},
\intro{weakening} and \intro{exchange} respectively (\cref{fig:substructural}).

\begin{marginfigure}
  \small%
  \begin{mathpar}
      \inferrule[{[Weakening]}]{
          \Delta, A \vdash C
      }{
          \Delta \vdash C}
      \\
      \inferrule[{[Contraction]}]{
          \Delta, A, A \vdash C
      }{
          \Delta, A \vdash C}
      \\
      \inferrule[{[Exchange]}]{
          \Delta_1, B, A, \Delta_2 \vdash C
      }{
          \Delta_1, A, B, \Delta_2 \vdash C}
    \\
  \end{mathpar}
  \caption{Substructural sequent calculus rules.}\label{fig:substructural}
\end{marginfigure}

However, the first is \emph{unsound} for separation logic assertions, and the
second is unsuitable for \kl{CN}'s use case. So, \kl{CN} must use \kl{separation
logic} assumptions \intro{linearly}~\sidecite{girard1987linear}; other
assumptions, such as simple or \kl{refinement types}, can be used without
restriction.
\begin{itemize}
    \item Duplicating assumptions relies on
        \sm{A \Rightarrow A \wedge A} in \kl{intuitionistic} logic. However, the
        same is not true for \sm{\ast} in separation logic:
        \sm{A \nRightarrow A \ast A}. This is because assertions have their
        semantics defined with reference to a heap. For example, a heap
        satisfies \sm{A_1 \ast A_2} iff it can be split into two disjoint
        sub-heaps which satisfy \sm{A_1} and \sm{A_2} separately. If \sm{A = (x
        \mapsto y)}, then there is one heap satisfying \sm{A}, but none
        for \sm{A \ast A}.
    \item Forgetting assumptions relies on whether the user cares about memory
        leaks or not (the C standard does not make memory leaks an
        error). The intended use of \kl{CN} in resource constrained settings
        leans us towards explicit deallocation and
        \emph{erroring when we forget to}.\sidenote{Though not yet supported by
            \kl{CN}, concurrency also requires being explicit about destroying
            a resource, for example, to prevent a user from acquiring the same
        lock twice.}
\end{itemize}

This is in contrast to the drop trait in
Rust,\sidenote{\url{https://doc.rust-lang.org/std/ops/trait.Drop.html}} or RAII
(Resource Acquisition Is Initialisation) in
C++,\sidenote{\url{https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines\#Re-raii}}.
These allow the programmer to elide explicit deallocation, by automatically
inserting such code before scope exits. Modelling that would
require \kl{weakening}, and make resource types \intro{affine}.

For completeness, a relevant logic is one which supports
\kl{contraction} and \kl{exchange} but not \kl{weakening}. In practice this
means relevant assumptions may not be implicitly dropped, but may be used one
or more time.

\kl{Linear} types may be necessary, but they can be cumbersome, because their
corresponding terms \textemdash{} which I refer to as \kl{permissions} or
\kl{resource terms} \textemdash{} must be threaded through most operations. For
example, dereferencing a pointer requires a permission, but must also
\emph{return} one, so that the pointer may be dereferenced again. Such
threading is tedious and often obvious, so in \kl{CN} it is implicit and
automated (\S\ref{sec:elaboration}). I refer that automation to as
\kl{resource inference}.

\begin{marginfigure}
  \small%
  \begin{mathpar}
      %\inferrule[Declarative Var]{
      %}{
      %    x {:} t \vdash x {:} t}
      %\\
      %\inferrule[Algorithmic Var]{
      %}{
      %    \Gamma , x {:} t \vdash  x {:} t \dashv \Gamma'}
      %\\
      %\{\, x {:} t \,\} = \Gamma' - \Gamma
      %\\
      \inferrule[{[Declarative Pair]}]{
          \Delta_1 \vdash e_1 {:} T_1
          \and
          \Delta_2 \vdash e_2 {:} T_2

      \\

          \\
          \Gamma_2 \vdash e_2 {:} T_2 \dashv \Gamma_3
      }{
          \Gamma_1 \vdash (e_1, e_2) {:} T_1 \times T_2 \dashv \Gamma_3}
      \\
      \Delta_1 = \Gamma_2 - \Gamma_1 \and \Delta_2 = \Gamma_3 - \Gamma_2
  \end{mathpar}
  \caption{\intro{Declarative} ($\Delta$) versus \intro{algorithmic} ($\Gamma$) typing for
  linear pairs. A \kl{declarative} system is easier to describe and

For formalising \kl{Kernel CN}, I do use explicit \kl{permissions}, since that
makes the system easier to state and prove sound. And for clarity and
convenience, I also write linear components \kl{declaratively}
(\cref{fig:decl-alg}). \kl{Explicit permissions} also make it easy to specify
and explain the \kl{CN} \kl{resource (term) inference} algorithms as an
\emph{elaboration}, which I do in \fancyref{sec:elaboration}.\sidenote{I have
not embarked on any proofs about the elaboration rules.} Those rules use the
linear context in an algorithmic manner.

\section{Precise assertions for instantiating quantifiers without
backtracking}\label{sec:precise-assertion-inferring}

Prima facie, \kl{separation logic} types are in tension with \kl{liquid types}.
The former supports arbitrary quantifiers, which are often sufficient to write
expressive specifications to prove the absence of \kl{UB} and full functional
correctness; the latter restricts quantifiers to ones corresponding to program
values (function arguments for \sm{\forall}, and return values for \sm{\exists}), to
avoid sending quantified constraints to the SMT solver.

Alongside automating obvious proofs (using an SMT solver), and automating
\kl{permission} passing (with \kl{resource (term) inference}), we would also,
like to automate obvious \emph{quantifier instantiation}.\sidenote{Note that
this is not at all related to \emph{inferring specifications}, which is a
large and challenging problem in its own right.}

To better understand this problem, let us recall the \kl{separation logic}
proof sketch of integer linked list append from
\cref{fig:append-annot,fig:list-pred}, reproduced in
\cref{fig:append-annot-formal,fig:list-pred-formal} for convenience.

\begin{marginfigure}
    \small%
    \centering
    \begin{align*}
        \mathrm{list} &(\mathsf{p}, l) \mathrel{{=}^\mathrm{def}} \\
                      &\mathsf{emp} \ast (\mathsf{p} = \mathsf{NULL} \wedge l = []) \\
                      &\vee \exists \; {head}, \; {tl}, \mathsf{p\_tail}.\\
                      &\vee \exists \; {head}, \; {tl}, \mathsf{p\_tail}.\\
                      &\qquad (\mathsf{p} \mapsto {head}) \\
                      &\qquad \ast (\mathsf{p} + 1 \mapsto \mathsf{p\_tail}) \\
                      &\qquad \ast \mathrm{list} (\mathsf{p\_tail}, {tl}) \\
                      &\qquad \ast l = {head} {:}{:} {tl}
    \end{align*}%
    \caption{Definition of a recursive list predicate in a simple separation
        logic.}\label{fig:list-pred-formal}
\end{marginfigure}

We see that, the specification (implicitly) quantifies over pointers
\sm{\mathsf{xs}} and \sm{\mathsf{ys}}, corresponding to the function arguments. It
also quantifies over \emph{logical (ghost) lists} \sm{l_1} and \sm{l_2}.
Following a strict \kl{liquid typing} discipline would mean the user would have
to manually instantiate them at each call site (line 9). The user would also
have to do the same for the existential quantifiers of the \sm{\mathrm{list}}
predicate of~\cref{fig:list-pred-formal}, when folding it (line 12).

\begin{figure}[h]
    \inputminted[breaklines,linenos,mathescape,fontsize=\small]{py}{code/append_annot.py}

        append.}\label{fig:append-annot-formal}
\end{figure}

% \sidenote{I discuss quantifiers related to array reasoning in~\cref{sec:it-array}.}

This is irksome because because the arguments to \mintinline{py}{append}, and
the first argument to \sm{\mathrm{list}}, uniquely determine all the required
instantiations at lines 9 and 12 respectively. So, a simple inference scheme
would be to scan the context for predicates which match part of the goal based
on shape and \emph{computational} arguments, and instantiate any quantifiers
based on its remaining arguments.

In this instance, when calling \mintinline{py}{append(xs->tail, ys)}, % chktex 36
such an inference scheme would
\begin{enumerate}
    \item Delay instantiating \sm{l_1} and \sm{l_2}.
    \item Note that the precondition requires \sm{\mathrm{list}(\mathsf{xs}',
        l_1)} and \sm{\mathrm{list}(\mathsf{ys}', l_2)}.
    \item Check the context for a match with \sm{\mathrm{list}(\mathsf{xs}',
        \_)}.\sidenote{Checking whether two symbolic terms are equal can be
        automated with an SMT solver.}
    \item Find \sm{\mathrm{list}(\mathsf{xs}', l_1')}.
    \item Select \sm{[l_1' / l_1]} as its instantiation.
    \item Repeat similarly for \sm{\mathsf{ys}} and \sm{l_2'}.
\end{enumerate}

This is a cute idea, but it glosses over several details, such as
\begin{enumerate}
    \item Are such assertions characterisable, and if so, how?
    \item Can such a scheme handle disjunction, \sm{P \vee Q}?
    \item Are assertions where \kl{computational} arguments uniquely determine
        \kl{logical arguments}, expressive enough for realistic code?
    \item What is the correct `atomic' predicate to look up in a context?
    \item Do all assertions decompose to a context of `atomic'
        predicates?
    \item Should it unfold \kl(CN){recursive predicates}, and if so, when?
\end{enumerate}

I tackle the first three questions here, and leave the latter three
to be discussed in~\fancyref{sec:heap-types}.

For the first question, the answer is: in practice, \emph{yes}. If one assigns
input and output \kl{modes} to the arguments of \kl{separation logic}
predicates, and ensures that predicates are \emph{mode-correct} via a syntactic
check (\fancyref{sec:monadic-syntax}), then that suffices to guarantee that the
system can \emph{always infer quantifiers}.%
\sidenote{The theoretical justification for this unclear. Such assertions happen
to be characterisable as \kl{precise}~\cite{reynolds2008intro}, but the
connection to \kl{modes} is unknown.}%
\margincite{reynolds2008intro}

\subsection{Precise assertions}\label{subsec:precise-assertion}

\begin{definition}[Precise assertions]%
\label{def:precise-assertion}
    \AP{} An assertion \sm{Q} is \intro{precise} iff, for all stores \sm{s}, and heaps
    \sm{h}, there is at most one \sm{h' \subseteq h} such that \sm{h' \in [\![ Q ]\!] (s)}.

    In other words, if a \kl{precise} assertion holds on a subheap, then it
    does so uniquely.
\end{definition}

Some examples and properties of precise assertions as shown
in~\cref{fig:precise}; the same for of imprecise assertions are shown
in~\cref{fig:imprecise}. As I shall show later, each production in the grammar
for \kl{linear} \kl{resource types} (\cref{fig:kernel-res}), stays within the
precise fragment.

\begin{marginfigure}
\small%
\begin{mathpar}
    \mathsf{emp}
    \and p \mapsto v
    \and \exists \; v.\ p \mapsto v
    \and \mathrm{list}(\mathsf{p}, l)
    \and \exists \; l.\ \mathrm{list}(\mathsf{p}, l)
    \and P \wedge Q \text{ when $P$ or $Q$ is precise}
    \and P \ast Q \text{ when $P$ and $Q$ are precise}
\end{mathpar}%
\caption{Some examples and properties of precise assertions.}\label{fig:precise}
\end{marginfigure}

\citeauthor{brotherston2016model}~\sidecite{brotherston2016model}~showed that
precise assertions and an \kl{ordered-disjunction} allow for efficient (polynomial time)
model checking without backtracking (since a normal disjunction is enough to
require backtracking and thus exponential).
% in~\fancyref{sec:elaboration}, I
% show how the same allow for \kl{CN} to infer instantiations of quantifiers
% without backtracking. I do so by leaning on input and output \kl{modes} which
% (a) is intuitive, given that in C source a pointer is an ``input'' and
% dereferenced value an ``output'' and (b) happens to coincide.

This leads to answering the second question on disjunctions. As visible from
\cref{fig:imprecise}, disjunctive assertions can be imprecise. Yet, from
\cref{fig:precise}, we see that the list predicate, and even a version of it
which is existentially quantified over its \kl{ghost list}, fits the definition of
precise (\cref{fig:list-pred-formal}).

\begin{marginfigure}
\small%
\begin{mathpar}
    \mathsf{true}
    \and \mathsf{emp} \vee \mathsf{x} \mapsto 42
    \and \mathsf{x} \mapsto 3 \vee \mathsf{y} \mapsto 7
    \and \exists \; \mathsf{p}.\ \mathsf{p} \mapsto 1
    \and \exists \; \mathsf{p}.\ \mathrm{list}(\mathsf{p}, l).
\end{mathpar}
\caption{Examples of im\kl{precise} assertions.}\label{fig:imprecise}
\end{marginfigure}

How so? Informally, the two arms of the disjunction make assertions which are
disjoint on \emph{both} the value of the computational parameter \sm{\mathsf{p}}
\emph{and} on the shape of the heap; one branch says \sm{\mathsf{p} =
\mathsf{NULL}} and the heap will be \sm{\mathsf{empty}}, whereas the other branch
guarantees that (implicitly) \sm{\mathsf{p} \neq \mathsf{NULL}} and that the heap
will have \emph{at least two} heap cells. The cells' locations, and thus the
values they point to, \sm{\mathsf{head}} and \sm{\mathsf{p\_tail}}, are wholly
determined by \sm{\mathsf{p}}, even though they are existentially quantified. This
means the recursive call is also precise, and why \sm{{tl}} is also (recursively)
wholly determined by \sm{\mathsf{p}}, despite also being existentially quantified.

This style of reasoning, of starting with computational parameters, and
ensuring that all existentially quantified values are wholly determined by
them, can be operationalised as a \kl{mode} discipline for predicate arguments,
which I shall discuss in \fancyref{sec:monadic-syntax}. For now, it suffices to
say disjunctions can be compatible with precision; on how to ensure this, I
will imminently return.

Finally, the third question, of whether precise assertions are expressive
enough for realistic code, is an empirical one. Our experience using \kl{CN} so
far~\sidecite{pulte2023cn,pulte2024tutorial,aamer2026code} suggests the answer
is yes, it is sufficient for small to medium tutorial examples, all the way up
to specifying the different allocators (\S\ref{chap:buddy}) used in \kl{pKVM}\@.

That being said, we have found that introducing and instantiating quantifiers
manually can actually be more ergonomic, as discovered by Cassia Torczon whilst
verifying a basic string manipulation library in \kl{CN}.%
\sidenote{\href{https://github.com/rems-project/cerberus/issues/540}{Cerberus\#540}}

The representation of strings in this library are null-terminated arrays of
characters. Because the length is unknown, and the direction of traversal
fixed, null-terminated strings are natural to describe using a \kl(CN){recursive
predicate}. However, the library functions are implemented using while-loops and
array-indexing, for which it is convenient (but not necessary) for proof (and
library clients) to express strings as an array (represented by an iterated
predicate), over a finite range. The end of that range is the string's length,
which is not available in the code, especially before traversing the string.
However, to prove all indexing is within bounds, we need to be able to refer to
the string's length in the precondition and loop-invariants. Therefore, being
able to introduce and instantiate the string's length manually makes the proof
more convenient.

\section{Monadic syntax for mode-correctness}\label{sec:monadic-syntax}

We can use \intro{modes} to ensure that we can infer quantifier instantiations.
Start with separation logic predicates, and label their arguments as either
inputs or outputs, as shown in~\cref{fig:mode-pred}. In
the scope of each quantifier, for each predicate, check the mode of each
parameter matches the mode of each argument. Computational arguments are
considered inputs. If a quantified variable is used in an input position, it
must also be used elsewhere in an output position.

\begin{marginfigure}
    \centering
    \small%
    \begin{align*}
        \_ \mapsto \_ \:&: \mathrm{Loc}^{\mathsf{in}} \times \mathrm{Value}^{\mathsf{out}} \rightarrow \mathrm{Prop} \\
        \mathrm{list} \:&: \mathrm{Loc}^{\mathsf{in}} \times \mathrm{IntList}^{\mathsf{out}} \rightarrow \mathrm{Prop}
    \end{align*}
    \caption{Modes on separation logic predicates.}\label{fig:mode-pred}
\end{marginfigure}

Revisiting the second disjunct of~\cref{fig:list-pred-formal}, the
quantified variable \sm{\mathsf{p\_tail}}, occurs in \sm{\mathrm{list}
(\mathsf{p\_tail}, {tl})} in the input position, but this is fine because it also
occurs in the output position in \sm{\mathsf{p} + 1 \mapsto \mathsf{p\_tail}}.
However, in the example from~\cref{fig:imprecise}, \sm{\exists \; \mathsf{xs}. \
\mathrm{list}(\mathsf{xs},l)} is badly moded because \sm{\mathsf{xs}} occurs in an
input position, but nowhere else in an output.

Ensuring that quantifiers preserve \kl{precision} in assertions by
dividing predicate arguments into input and output modes is
not new~\sidecite{somogyi1996execution,berdine2006smallfoot,nguyen2008runtime,maksimovic2021gillian},
including for the purposes of reducing the burden of
annotation~\sidecite{jacobs2011verifast}.

What is new is the target audience of kernel programmers, rather than
verification specialists. Programmers may not be used to thinking in terms of
ghost state, and discussions with our users suggest that adding quantifiers and
\kl{mode}s on top of that would be step too far.

An elegant solution to both inscrutable mode rules, and the problem of
disjunctions mentioned earlier, is to change the perspective on
\cref{fig:mode-pred}~\sidecite{krishnaswami2022monadic}. A predicate
\sm{\mathrm{list} : \mathrm{Loc} \times \mathrm{IntList} \rightarrow
\mathrm{Prop}}, considered set-theoretically is just \sm{\mathcal{P} (\mathrm{Loc}
\times \mathrm{IntList})}, which is isomorphic to \sm{\mathrm{Loc} \rightarrow
\mathcal{P} (\mathrm{IntList})}. Unlike the initial form, which gave ``equal
weighting'' to input and outputs, this form makes the input role of
\sm{\mathrm{Loc}} and the output role of \sm{\mathrm{IntList}}, inside a covariant
powerset monad, very natural.

\begin{marginfigure}
    \small%
    \begin{align*}
        &\llbracket \_ \rrbracket \::\: \tau \rightarrow (\tau \rightarrow \mathsf{Prop}) \\
        &\llbracket \mathsf{return}\ t \rrbracket = \lambda a.\ t = a \wedge \mathsf{emp} \\
        &\llbracket \mathsf{Own(t)} \rrbracket = \lambda a.\ t \mapsto a \\
        &\llbracket \mathsf{let\ x} = e; e' \rrbracket \\
        &\: = \lambda a.\ \exists \; x.\ \llbracket e \rrbracket x \ast \llbracket e' \rrbracket a \\
        &\llbracket \mathsf{if}\ t\ \mathsf{then}\ e\ \mathsf{else}\ e' \rrbracket \\
        &\: = \lambda a.\  \left( t \wedge \llbracket e \rrbracket a \right) \vee \left( \neg \; t \wedge \llbracket e' \rrbracket a \right)
    \end{align*}
    \caption{\intro{Monadic syntax} for separation logic, along with a translation into the traditional presentations. Pure
        terms are denoted by $t$, and \kl{monadic} expression are denoted with $e$.}\label{fig:monad-sl}
\end{marginfigure}

This notational transformation turns \emph{mode correctness} into
\emph{variable scoping}, when one interprets let-bindings \sm{\mathsf{let\ x} = e;
e'} as \kl{monadic} bindings inside a covariant powerset monad. It also enforces the
disjointness of computational values and the shape of the heap mentioned
earlier with the \sm{\mathsf{if}\ t\ \mathsf{then}\ e\ \mathsf{else}\ e'}
construct. Thus, all logical quantifiers can be \emph{inferred} without
backtracking, and branching assertions can be checked similarly:
check \sm{e} if you can can prove \sm{t}, or check \sm{e'} if you can prove \sm{\neg\;t}.

\section{Iterated separating conjunctions to handle arrays}\label{sec:it-array}

C programmers use arrays a lot, particularly with computed index (\ie{}
`random') access, rather than following a particular traversal pattern.
Verification tools typically handle arrays via \kl(CN){recursive predicates}, and if the order of
traversal in C does not match the order of traversal in the predicate, or
access to the middle of the array is required, then a user needs to use lemmas,
or rely on heuristic-based automation, to massage the available assumptions into a usable form.

\kl{CN} implements \kl(CN){iterated separating conjunctions}, henceforth referred as
\intro(kernel){iterated predicates}, inspired by \sidetextcite{muller2016automatic},
but with restrictions to ensure only quantifier-free SMT queries. They are
introduced and eliminated as follows.
\begin{itemize}
\item \sm{\cnkw{each}  \left(  \beta \,  \cnmv{x} \, ;  \cnnt{iguard}
    \right)\, \left\{  { \alpha }  \left(  \cnkw{array\_shift} \, \langle
    \tau  \rangle  \left(  { y_p }  \cnsym{,}  \cnmv{x}  \right)  \cnsym{,}
    \cnnt{iargs}  \right)  \, \right\}}. % chktex 25
\begin{itemize}
    \item \sm{\beta} is the type of the quantifier (usually % chktex 25
        \cninline{u64}).
    \item \sm{\cnmv{x}} is the iterated variable. \item \sm{\cnnt{iguard}} is the index
        guard, a boolean-valued logical/SMT expression on the iterated variable
        \sm{\cnmv{x}}.
    \item \sm{{ \alpha }} is the name of a predicate.
    \item \sm{\cnkw{array\_shift} \, \langle  \tau  \rangle  \left(  { y_p }  \cnsym{,}  \cnmv{x}  \right)} is \kl{CN} syntax for C % chktex 25
        pointer-arithmetic \sm{{ y_p } \,  \mathbin{ \symtt{+} }  \, \cnmv{x}} where the base pointer \sm{{ y_p }}
        has C type \sm{\tau  \cnsym{*}}. This requires the first argument of any
        \sm{{ \alpha }} to be a pointer.
    \item \sm{\cnnt{iargs}} is a list of logical/SMT arguments.
\end{itemize}
\item The user must explicitly declare which indices can be moved in or out
    with a `\sm{\cnkw{focus}\ \alpha,\ \cnnt{term}\cnkw{;}}'
    \kl{CN statement}.
\end{itemize}

This enables a few features conveniently.
\begin{itemize}
    \item \kl(CN){Iterated predicates} can be tested for equality by
        looking only at the name of the predicate, symbolic
        equality of the base pointer and input arguments, and symbolic equivalence of the guard
        conditions.
    \item Moving or updating indices for \kl(CN){iterated predicates} can be automated.
    \item \kl(CN){Iterated predicates} can be split along an arbitrary
        guard automatically:
        for guard \cninline{A = 0i32 <= i && i < 10i32} and guard
        \cninline[breaklines]{B = A && mod(i, 2i32) == 0i32}, % chktex 36
        the subtraction is simply \cninline{A && !B}. Note that the split % chktex 26
        does not have to be contiguous.
\end{itemize}

It also comes with a few limitations.
\begin{itemize}
    \item It does not support automatically \emph{merging} arrays, because the
        constraints required to express the \emph{merged values} are outside
        the \kl{decidable fragment for the SMT theory} of arrays.\sidenote{\kl{CN}
        could, but does not, support merging for uninitialised arrays.}
    \item It does not make it clear what the lower and upper bounds of the
        iteration is. This would be useful for both disjointness reasoning in
        proof mode, and runtime checking for
        Fulminate~\sidecite{banerjee2025fulminate}.
\end{itemize}

\kl{CN} did support the \kl{decidable} array property
fragment~\sidecite{bradley2006whats}, but it was not expressive enough for
verifying \kl{pKVM}'s \kl{buddy allocator} (\S\ref{chap:buddy}) and so it was
removed. \kl{CN} also inferred indices (instead of
requiring the movable ones to be declared up front), but this was removed
during a change to the inference
scheme.\sidenote{\href{https://github.com/rems-project/cerberus/commit/7c2c0a364a4373e4eb109f32d01cc9584f51e81f}{Commit
7c2c0a36.}}\label{sn:new-inf}
